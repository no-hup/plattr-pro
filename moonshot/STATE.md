## Decisions log
| Date | Decision | Why |
|---|---|---|
| 2026-09-17 | **Printing is a print agent on the restaurant's LAN that pulls jobs**, not a browser holding a link (KT-D1, KT-D1b) | A page cannot open a TCP socket, and the Bluetooth alternative meant replacing every printer a restaurant owns. Because the agent pulls, nothing on the LAN is addressable and no certificate is needed. It also removes the browser from the print path entirely, which is what made "till and kitchen tablet both print" cost nothing. The price is hardware per restaurant, a setup visit, and a second deployable with no update or monitoring story (TD-032) |
| 2026-09-17 | **`categoryId` is frozen onto the placed line** (KT-D2) | Schema. One additive field so a ticket routes by what the menu said when the round was placed, not when it is reprinted. Without it a station beyond kitchen/bar needs this migration later, after there is data |
| 2026-09-17 | **A staff member can open a table session with no OTP** (`table-openTable`, OR-1) | Session semantics. A walk-in has no phone, and `validateOTP` was the only thing that minted a table session. The session records `openedBy: 'staff:<serverId>'`. The exposure it adds — a table open with no guest verified — already exists for every OTP'd table |
| 2026-09-17 | **Opening an occupied table extends the live sitting and never mints a new one**; the four-hour expiry becomes `ordering.sessionHours` (OR-6) | Session lifetime, and it reaches the **guest** app too because `validateTableSession` is shared. Otherwise a 23:05 round on a table opened at 19:00 silently starts a second bill. A guest at a long dinner also stops being logged out mid-meal |
| 2026-09-17 | **UPI provider is Paytm**, and phases 1–6 ship with no provider at all (UQ-2, UQ-2b) | 0 % against Razorpay's ~2.36 % is ~₹21,000 a month on ₹9 lakh of UPI. What is given up is documentation: Paytm publishes no webhook retry policy, no dedupe key and no ordering guarantee, so phase 7 measures them in sandbox before trusting them. The adapter is one file, so the switch stays cheap |
| 2026-09-17 | **A public HTTP webhook endpoint on the production project is accepted** (UQ-3) | The first endpoint on `rms-app-dd875` anyone on the internet can reach. Raw-body HMAC checked before anything is read, constant-time compare, secret in Secret Manager. There is no automatic payment confirmation without one, and a forged request costs one hash and no Firestore read |
| 2026-09-16 | **`line.sent` is written for real.** A line is born `sent: true` at checkout; behind the waiter-confirmation gate it is born `false` and the waiter's confirm flips it. It was hardcoded `false` on every line ever written | That made ST's whole `lineSent` branch unreachable: **ST-S5 had never once fired**, every void anywhere was judged "not yet sent" — no PIN, logged P1 instead of P0 — and R8's "a SERVER cannot void a sent line" let a captain void food already cooking. Turning it on changes behaviour for live restaurants, which is why it is here and not in a commit message. Only `approvals-apply` reads it, and its one caller is the till, which already has the PIN interceptor |
| 2026-09-16 | **Waiter-confirmation gate is `ordering.requireWaiterConfirmation` on `config/settings`**, default false. A guest-placed round lands on `AWAITING_CONFIRMATION`, is withheld from the kitchen read, and the waiter confirms it to `PENDING`. Rejecting is an ordinary cancel | Its own namespace beside `approvals` (ST) and `tax` (BL) rather than the `featureFlags` block, which is a different and already overloaded thing. Not the FeatureFlags singleton: that is process-global and this has to differ per restaurant. Read out-of-band in `createOrUpdateOrder` in that file's own style (`loadChargesConfig`, `loadTaxBlocks`) rather than through `app/config.ts`, because it is existing flat-dir code |
| 2026-09-16 | **Cancelling a cart takes its lines off the bill, and is recorded but not gated** (TD-023) | Nothing but ST's own void path ever set `countsTowardTotal: false`, so a cancelled or rejected round stayed billable at the till. Fixed at `_updateCartStatus` so every caller gets it — kitchen cancel, waiter cancel, guest order rejected — not just the new reject path. The PIN half waits on TD-003 |
| 2026-09-16 | **Detection over prevention.** Assume one trusted account holder, record every act that a person chose to take, accept a day of exposure, and catch it the next morning. Correctness and compliance are excluded and are still prevented: client-sent money, hard deletes, tax rates, number series | Three sessions of agents in a row reached for a new gate whenever money appeared, which is the right instinct and the wrong default. A gate is friction that gets routed around — shared PINs, a feature nobody uses — and a control people route around is worse than none, because you think you have one. The trail is also where we beat the incumbents, who only produce reports. Written as "Catch it, don't cage it" in `CLAUDE.md`, with the clause that it can never excuse a missing test, check or audit row: detection is a harder bar than prevention, because a gate fails loudly and a missing audit row fails silently |
| 2026-09-16 | The audit trail is designed as an **agent's input**, not as paperwork: judgeable without joining five collections, and a quiet day distinguishable from a day whose logging broke | A monitor that cannot tell "nothing happened" from "nothing was written" reports a clean night either way. Cheap to decide now, a migration later |
| 2026-09-15 | Manual discount is cashier-only: the till logs in as an existing MANAGER (or ADMIN) account. SERVER role gets 403. No new role | "Cashier" is a seat, not a role; reuse `adminApp/auth.js` roles |
| 2026-09-15 | Server decides when a PIN is needed. Under the limit: applied at once. Over: backend returns `permission-denied` + `{requires:'pin'}`, till shows the PIN popup, resends with `pin`, backend checks it against that same account's hashed PIN (`servers/{id}.password`) | Same pattern the consumer app uses for `unauthenticated` → `AuthPrompt`; the till is new code so it gets its own handler |
| 2026-09-15 | Every manual discount writes one audit row with a severity: `P1` under the limit, `P0` over it. Report groups by severity and staff | Count of P0s per cashier per week is the theft signal |
| 2026-09-15 | Limit is a config key (`discount.pinAbovePercent`, lean 10). PO-Q1 still open on rupees-vs-percent | Config not code |
| 2026-09-15 | Donor clones live outside the repo at `~/Desktop/moonshot/donors/`; `DONORS.md` is the index and the recreate commands | Greps stay clean; disk is at 97%, so sparse and shallow only |
| 2026-09-15 | Firebase stays; domain layer must not import it | Port later without a rewrite |
| 2026-09-15 | React web for staff screens, not Flutter | Agents can drive a real DOM; Flutter web is canvas |
| 2026-09-15 | Config document per restaurant, lint bans `restaurantId ===` | Variation as data, not branches |
