Date: 2026-09-17. Donors read: **Odoo 19-ish** (`point_of_sale`, `pos_restaurant`),
**URY** (Frappe/ERPNext, Indian restaurant POS), **SambaPOS** fragments, **Dolibarr** fragments.

## 1. Routing — how a ticket reaches the right printer

### URY: two-level mapping, product→**item group**→**production unit**→printer

The routing key is **not** the product and **not** the menu category the guest sees.
It is ERPNext's `Item.item_group`, mapped to a **URY Production Unit** (a physical
kitchen station — hot kitchen, bar, tandoor), which then owns a list of printers.

- A production unit holds a child table of item groups:
  `ury/ury/api/ury_kot_generate.py:142-153` reads `URY Production Item Groups` for
  `parent = <production unit>`, `order_by="idx"`.
- Items are bucketed per production unit and **one KOT document per unit** is created:
  `ury_kot_generate.py:154-184`. A four-item order spanning kitchen and bar produces
  two `URY KOT` docs, each printed separately.
- The KOT doc's `on_submit` does the actual printing:
  `ury/ury/doctype/ury_kot/ury_kot.py:12-14` → `multi_print_kot()`.
- Printer resolution is a **three-tier fallback**, in this order
  (`ury_kot.py:38-83`):
  1. **Production Unit** printers (`parenttype: "URY Production Unit"`,
     `custom_kot_print: 1`) — `ury_kot.py:39-44`.
  2. **Room** printers (`parenttype: "URY Room"`), consulted *in addition*, only for a
     real dine-in table — `ury_kot.py:57-73`.
  3. **POS Profile** printers as the fallback when neither fired — `ury_kot.py:75-83`.
  All three queries are `order_by="idx"` — the row order in the child table is the
  print order, and **every matching printer gets a copy** (it's a loop, not a pick).

The **bill** routes differently again: room-level first, POS-profile-level otherwise —
`ury/ury/api/ury_print.py:94-124`. Bill printers are selected by a `bill: 1` checkbox
on the same `URY Printer Settings` child row
(`ury/ury/doctype/ury_printer_settings/ury_printer_settings.json` has only
`bill` + `printer`; `custom_kot_print`, `custom_kot_print_format`,
`custom_waiter_print`, `custom_waiter_print_format` and `custom_block_takeaway_kot`
are custom fields bolted on later — `ury/ury/custom/ury_printer_settings.json`).
So **one child row = one printer = a set of role checkboxes**. A single physical
printer can be the bill printer *and* a KOT printer for a station, by ticking two
boxes on the same row. That is their answer to printer sharing.

**Product that maps to nothing:** it is silently dropped from every KOT, and the
cashier gets a `msgprint` toast — `ury_kot_generate.py:134-140`:

```python
if item_group not in all_production_item_groups:
    frappe.msgprint(f"Item group '{item_group}' for item '{item_code}' is not in any production.")
```

It is a *message*, not a `throw`. The order still saves and bills fine; the kitchen
simply never hears about the dish. This is the single worst behaviour in either donor.

**No production unit at all** is a hard stop — `ury_kot_generate.py:185-188` throws
"Create URY Production unit against POS Profile". But note the asymmetry:
zero production units = refuse to take the order; one production unit that doesn't
cover this item = take the order and lose the item.

There is a **second** hole in the same area. `multi_print_kot`'s entire body is
nested under `if self.production:` (`ury_kot.py:38`), and the POS-profile fallback at
`ury_kot.py:75-78` is nested *inside* `if production_unit_printers:` at line 47.
So a production unit that exists but has **no printer rows configured** prints
nothing anywhere — not even the POS fallback that was fetched at line 30 for exactly
that case. The `pos_print_flag` variable was clearly written to prevent this and the
indentation defeats it.

**Mapping changed after the order was placed:** URY re-resolves the mapping at every
KOT creation (`ury_kot_generate.py:124-159` runs per submit, not per order). A round
fired at 19:00 and a round fired at 19:40 can land on different printers if someone
edited the production unit in between. There is no snapshot. The `URY KOT` doc *does*
store `production` (`ury_kot_generate.py:56`), so the history of where it went is kept,
but a **reprint** does not use it: `ury/ury/api/ury_kot_reprint.py:68` re-picks the
printer from the POS Profile by order type, completely bypassing the production unit:

```python
printer = table_order_printer if order_type == "Dine In" else parcel_order_printer
```

A reprint can therefore come out of a different printer than the original.

### Odoo: printer→**POS category** many-to-many, and only the *first* category counts

- `odoo/addons/point_of_sale/models/pos_printer.py:44`:
  `product_categories_ids = fields.Many2many('pos.category', 'printer_category_rel', ...)`.
  The routing key is the POS category (the customer-facing one), not a separate
  kitchen-station taxonomy. Printers attach to a config via
  `pos_config_ids` (`pos_printer.py:46`), and the whole printer list is pushed to the
  browser at session load (`pos_printer.py:60-62`, `pos_session.py:140`).
- The filtering of lines→printer happens client-side in `point_of_sale/static`, which
  **is not in this clone**, so I cannot show you that `if`. What I *can* show is the
  restaurant-side summary that uses the same lookup and takes only the first category:
  `pos_restaurant/static/src/app/services/pos_store.js:486-500`, note
  `for (const category of categories.slice(0, 1))`. A product in both "Food" and
  "Cocktails" is counted as Food only, for the toast. Whether the actual print
  routing shares that `slice(0,1)` I could not verify from disk.
- **Product that maps to nothing / mapping changed later**: I could not find this in
  the cloned files. Odoo's snapshot (below) records only `product_id`, `name`, `note`,
  `quantity`, `attribute_value_ids` (`pos_restaurant/models/pos_session.py:27-34`) —
  **no printer id**. So a mapping change between rounds re-routes silently, same as URY.

## 2. What's on a kitchen ticket vs a bill

**Prices.** URY's KOT items child table carries `item`, `item_name`, `quantity`,
`cancelled_qty`, `comments`, `course` — **no price field anywhere**
(`ury_kot_generate.py:73-82`, `:317-327`). The waiter slip print format has exactly
two columns, Item and Qty
(`ury/ury/print_format/ury_waiter_order_slip/ury_waiter_order_slip.json`). The bill,
by contrast, is a full ERPNext invoice format with Sr / Item / Description / Quantity /
Stock UOM / rate / amount and the tax block
(`ury/ury/print_format/merged_pos_invoice_format/merged_pos_invoice_format.json`).
Odoo's kitchen ticket template likewise carries no money: the restaurant patch adds
only guest count and floor name to the header
(`pos_restaurant/static/src/store/order_change_receipt_template.xml:6-14`).

**Order number.** URY does something worth stealing. `POS Invoice.name` is a global
sequence nobody can read aloud, so they compute a **per-shift human number**:
`custom_ury_order_number = <last 5 digits of this invoice> − <last 5 digits of the
invoice that was current when the shift opened>` —
`ury/ury/api/ury_kot_order_number.py:18-25`. Shift open snapshots the baseline
(`ury_kot_order_number.py:86-100`). Aggregator (Swiggy/Zomato) orders get a
**separate counter and an "AGR - " prefix** (`:27-28`, `:55-63`, `:76`) so the kitchen
can tell a delivery ticket from a dine-in ticket at a glance. There is a
`custom_reset_order_number_daily` flag (`ury/hooks.py:428`). The number is stamped
onto every KOT (`ury_kot_generate.py:41`, `:59`) and printed as `Order:` on the
waiter slip. The fallback when the subtraction goes wrong is telling: if
`order_number <= 0` they print the raw invoice tail instead
(`ury_kot_order_number.py:36-43`) — i.e. an ugly number beats no number.

Odoo prints `pos_reference` and, for the kitchen ticket, the course and table.

**Modifiers / variants / notes.** Two different models:
- URY has **one free-text `comments` string per line** and nothing else
  (`ury_kot_generate.py:22`, which accepts either `comment` or `comments` from the
  client — a sign the field got renamed and they kept both). Crucially, the comment is
  **part of the line's identity** for aggregation: `key = (row.item, row.comments or "")`
  at `ury/ury/api/ury_waiter_print.py:34` and `:68`. Two "Paneer Tikka, no onion" and
  one plain "Paneer Tikka" stay two lines on the slip.
- Odoo has structured `attribute_value_ids` *inside the printed snapshot*
  (`pos_restaurant/models/pos_session.py:33`) plus a separate `note`, plus
  order-level `general_customer_note` and `internal_note` which are tracked as their
  own change types (`pos_store.js:504-512`, `:272-279`). A note edit alone triggers a
  ticket — `noteUpdate` is a first-class diff bucket alongside `new` and `cancelled`
  (`pos_store.js:264-271`).

**Line too long for the paper.** **Neither donor does column arithmetic.** Both render
HTML and let the layout engine wrap. URY's waiter slip pins the format to
`width: 80mm; max-width: 80mm; font-size: 14pt` and gives Item 70% / Qty 30%
(`ury_waiter_order_slip.json`, the `<style>` block and the `<th width="70%">`).
Odoo renders the receipt as DOM and rasterizes it. I found **no truncation, no
ellipsis, no character-count guard anywhere in either tree.** If you were expecting a
32/42-column ESC/POS text builder with wrapping rules, neither donor has one — they
both bought their way out of it by printing HTML through a driver that rasterizes.
That is a real architectural cost (below).

## 3. Knowing it printed

**Neither donor ever queries printer status.** No paper-out check, no cover-open
check, no `DLE EOT` status poll, in either tree. Say it plainly: there is no
printer health model in Odoo's `point_of_sale/models/` or anywhere in URY.

**URY: fire-and-forget for the kitchen, ack-and-mutate for the bill.**

The kitchen path swallows failures completely — `ury/ury/doctype/ury_kot/ury_kot.py:22-27`:

```python
def print_kot(printer, kot_print_format):
    try:
        print_by_server("URY KOT", self.name, printer, kot_print_format)
    except:
        pass
```

A bare `except: pass`. If the kitchen printer is off, the KOT document is still
submitted, the KDS still lights up, the guest is still charged, and nobody is told.
The waiter-slip path is better — it at least logs
(`ury/ury/api/ury_waiter_print.py:192-196`) — and it *pre*-validates that the print
format exists and is bound to the right doctype before trying
(`ury_waiter_print.py:130-153`).

The **bill** path is the opposite: the client only marks the invoice printed *after*
the driver's promise resolves. `ury/public/js/pos_print.js:117-130`:
`qz.print(...).then(→ qz_print_update)`, and the `.catch` at `:131-138` throws a
visible "Printing Failed". The CUPS path returns the literal string `"Success"` and
the caller string-compares it (`ury_print.py:75`, `pos_print.js:163`). Marking the
bill printed has a side effect beyond bookkeeping: it **releases the merged-table
cluster**, i.e. printing the bill is what frees the tables
(`ury_print.py:69-71`, `:155`, `:190-192`). That coupling is a decision, not an
accident, and it means a failed print leaves the table occupied — which is the safe
direction.

**URY's real safety net is a reconciler, not an ack.** A cron runs **every minute**
(`ury/hooks.py:206-211`) calling
`ury/ury/api/ury_kot_validation.py:kotValidationThread`. It finds POS Invoices in
draft state created between 5 minutes and 1 minute ago
(`ury_kot_validation.py:12-36` — the 1-minute lower bound is a grace window so an
order still being typed isn't swept), checks whether **any** KOT exists for that
invoice (`:49-55`), and if not, builds one, submits it (which prints it), tags it
`type: "Duplicate"` (`:105`), and writes a `URY KOT Error Log` row
(`:130-144`) plus a realtime push on a dedicated `kot_error_{branch}_{production}`
channel. The comment at `ury_kot_validation.py:146-149` explains why that channel is
separate — reusing `kot_update_...` would break the existing KDS because the payload
shape differs. That is a scar from a real incident.

**Duplicates are possible and they are labelled.** URY's `type` enum on a KOT is the
label: `"New Order"`, `"Order Modified"`, `"Partially cancelled"`, `"Cancelled"`,
`"Duplicate"`. The sweeper's output is explicitly `Duplicate`. Reprints of a bill are
blocked outright at the UI: `pos_print.js:50-56` re-fetches the invoice and throws
*"Invoice Already Billed — this order has already been billed, please reload"* if
`invoice_printed == 1`. Reprint of a *KOT* is a separate, permissioned, feature-flagged
action (`ury_kot_reprint.py:62-71`) — disabled by default, gated on
`custom_enable_kot_reprint`, and restricted to the captain who owns the order or
someone with elevated access (`ury_kot_reprint.py:42-47`).

**Odoo.** No status query either, and no retry loop I can point at (the printer
service is in the missing `static/` tree). What Odoo *does* have is a
**state-machine substitute for an ack**: the persisted `last_order_preparation_change`
is only advanced when a print is believed to have gone out, and the UI derives
"this order has unsent changes" from comparing live lines against it. The reprint
button only appears when `uiState.lastPrints.length` is non-zero and a printer is
configured (`pos_restaurant/.../actionpad_widget.xml:50-56`), so you cannot reprint
what was never printed. `nb_print` (`point_of_sale/models/pos_order.py:349`) counts
bill prints and is used for exactly one thing — refusing to change the payment of a
printed order (`pos_order.py:623-624`).

## 4. Changes after the ticket printed — **the interesting part**

The two donors chose opposite representations and it shows in everything downstream.

### Odoo: a persisted **snapshot of the last printed state**, diffed client-side

`pos.order.last_order_preparation_change` is a `Char` holding JSON; the help text is
literally *"Last printed state of the order"* —
`point_of_sale/models/pos_order.py:305`. Its shape is written out in
`pos_restaurant/models/pos_session.py:19-35`:

```python
last_order_preparation_change['lines'][orderline.uuid + " - "] = {
    "uuid", "name", "note", "product_id", "quantity", "attribute_value_ids"
}
```

Note the key: `uuid + " - "`. The trailing separator is there because the real
client-side key (`line.preparationKey`, used at `pos_store.js:149-150` and in the
tests at `pos_service.test.js:420`) is a **composite** — uuid plus something that
distinguishes otherwise-identical lines. The Python side writes the degenerate form
with an empty suffix. So a line's identity for printing purposes is *not* just its id.

The diff result — what actually gets printed — has three buckets plus two note slots:
`{ new, cancelled, noteUpdate, internal_note, general_customer_note }`
(`pos_store.js:264-279`, asserted in `pos_service.test.js:434-459`). So the answer to
"do they reprint everything, print a diff, or print a cancellation" is:
**they print a diff, and a cancellation is one bucket of that diff, on the same
ticket.** There is no separate cancellation document.

Three details around that are worth more than the mechanism itself:

- **`uiState.lastPrints` is an append-only list, not a single value.** Every print
  pushes its diff (`pos_store.js:287`). That is what makes reprint mean "reprint the
  last diff" rather than "reprint the whole order".
- **Merging two tables merges their print histories.** `_mergeOrders`
  (`pos_store.js:216-289`) takes the last print of each order and concatenates the
  `new`, `cancelled` and `noteUpdate` arrays into one combined entry (`:264-271`),
  and for the two note fields takes dest-or-source, not both (`:272-279`). The unit
  test at `pos_service.test.js:460-473` pins this: after merging, the surviving order
  has one `new` and one `cancelled` that came from *different* original orders.
- **Merging also has to move the printed-snapshot quantities, not just the lines.**
  `handlePreparationHistory` (`pos_store.js:148-172`) moves qty from the source
  order's snapshot into the destination's, splitting the entry when the moved qty is
  less than what was printed (`:163-170`). Without this, merging two tables that had
  each already sent 2× Naan would make the differ think 4 new Naans appeared.

**Sync conflict handling is the sharpest thing in the Odoo tree.** Two waiters on two
tablets both hold a local copy of "what the kitchen last saw". The server refuses to
let a stale one win — `point_of_sale/models/pos_order.py:396-416`:

```python
server_date = fields.Datetime.from_string(change['metadata'].get('serverDate'))
local_date  = fields.Datetime.from_string(local_change['metadata'].get('serverDate'))
if server_date > local_date:
    _logger.warning("Preparation changes were outdated, probably linked to a synching issue.")
    vals['last_order_preparation_change'] = record.last_order_preparation_change
else:
    local_change['metadata']['serverDate'] = fields.Datetime.now()...
```

The snapshot carries a `metadata.serverDate`; an incoming write older than what's
stored is **discarded and the server's version kept**. A snapshot with no metadata at
all is also refused (`:400-406`) — that's the old-document guard. The consequence to
internalise: *losing the write is the safe failure*. Keeping the server's older-but-
authoritative snapshot means the next diff may print an item twice; accepting a stale
client snapshot would mean an item never printing at all. They chose duplicate over
loss, deliberately.

### URY: **no snapshot** — the client sends before and after, the server diffs

`kot_execute(invoice_id, customer, restaurant_table, current_items, previous_items, comments)`
— `ury/ury/api/ury_kot_generate.py:336-343`. The client posts both arrays and the
server subtracts (`:355-356`, implemented at `:409-433`):

- `compare_two_array` finds items whose (item_code, qty) pair isn't in the old array
  and stores the **qty delta** (`:421`).
- `get_removed_items` finds item_codes present before and absent now (`:427-433`).
- Positive deltas → a **"New Order"** KOT, or **"Order Modified"** if a submitted KOT
  already exists for this invoice+production (`ury_kot_generate.py:162-171`).
- Negative deltas + removals → a **separate "Partially cancelled" KOT**
  (`:389-402`), on its own document, with its own `CNCL-`-prefixed naming series
  (`:362`).

So URY's answer is: **new items and cancellations are two different physical tickets.**
The cancel ticket back-links to the KOTs that originally carried those items —
`create_cancel_kot_doc` scans prior KOTs for a matching item_code and stores a
comma-joined `original_kot` string (`:271-287`). That's how the line cook finds the
ticket already on the rail.

The cancel ticket prints **`old_qty -> new_qty`, not a delta**
(`ury/ury/api/ury_waiter_print.py:82-101`, rendered at
`ury_waiter_order_slip.json`'s `{{ item.old_qty }} -> {{ item.new_qty }}` with a
`.cancel-line { color: #a00 }` class). "Chicken Biryani 3 -> 1" is unambiguous to a
cook in a way that "Chicken Biryani -2" is not. They also compute `old_qty` for
*additions* by reading the invoice's current qty and subtracting the delta
(`ury_waiter_print.py:90-101`), so a second round of the same dish prints "2 -> 5"
while a genuinely new dish prints a bare "3" (`display_mode: "single_qty"`).

A cancel KOT on the kitchen display requires a **manager to acknowledge it** —
`ury/ury/api/ury_kot_display.py:33-71`, `confirm_cancel_kot`, hard-gated on
`{"URY Manager", "URY Admin", "System Manager"}` and on branch, setting `verified`
and `verified_by`. The KDS surfaces cancel tickets differently
(`mosaic/src/components/kot.vue:62-70`, `:110-111`, `:459`, `:495-498`).

**Where URY's diff breaks.** `create_order_items` (`ury_kot_generate.py:15-25`)
carries **no line identity** — just `item_code`, `qty`, `item_name`, `comments` — and
`compare_two_array` matches on `item_code` alone (`:414`, `:419`). Two lines of the
same dish with different comments collapse: `b = filter(item_code == x.item_code)`
then `x.qty -= sum(all their qtys)`. Changing *only* a comment produces **no diff at
all** — `qty` is unchanged, so `compare_two_array` finds a match and emits nothing.
The kitchen never learns that "no chilli" was added. This is precisely the case
Odoo's `noteUpdate` bucket exists to catch. Note also the inconsistency: their own
waiter-slip aggregation *does* key on `(item, comments)`
(`ury_waiter_print.py:34`) — the display layer is more careful than the diff layer.

### SambaPOS: a third model — a **per-line `Locked` boolean**

`samba/Order.cs:32`: `public bool Locked { get; set; }`. Submitting a ticket locks
every line (`samba/Ticket.cs:522-530`). Unlocked lines are the ones not yet sent
(`Ticket.cs:493-496`, `:502`), and only unlocked lines are mergeable
(`OrderMerger.Merge` is fed `Orders.Where(x => !x.Locked && x.Id == 0)` —
`Ticket.cs:502-504`). The payoff is the guard at `Ticket.cs:487-491`:

```csharp
public bool CanCancelSelectedOrders(IEnumerable<Order> selectedOrders)
{
    var so = selectedOrders.ToList();
    return so.Count != 0 && so.All(x => !x.Locked) && !so.Any(x => x.Id > 0 || !Orders.Contains(x));
}
```

**A line the kitchen has seen cannot be plainly deleted — only voided.** This is the
cheapest possible version of the whole problem: one boolean per line, no JSON blob, no
before/after arrays. It cannot express "quantity reduced from 3 to 1" and it cannot
express a note change, but it gets the single most important rule right for free.
SambaPOS also stamps a per-round `OrderNumber` on newly-sent lines
(`Ticket.cs:511-514`) — that's the round number on the ticket.

## 5. Where the bytes are produced, and who holds the connection

**URY ships three different answers in one codebase, chosen per POS Profile** —
`ury/pos/src/lib/print.ts:16-42` is the whole decision in one function,
switching on `posProfile.print_type`:

1. **`qz`** — QZ Tray. The **server renders HTML**
   (`frappe.www.printview.get_html_and_style`, `pos_print.js:77-84`), the **browser
   opens a websocket to `localhost`** where a Java daemon is listening
   (`packages/core/src/print/qz.ts:26-28`, `qz.websocket.connect({ host, usingSecure: false })`),
   and the daemon hands the HTML to the OS printer
   (`qz.ts:52-57`: `qz.printers.getDefault()`, `type: 'html', format: 'plain'`).
   The browser is **not** on the wire with the printer; it is on a wire with a local
   agent that is. Cost: a Java install per till, plus a **code-signing problem** — QZ
   refuses unsigned print jobs, so every job payload must be RSA-signed. URY did this
   the wrong way first and then fixed it, and both versions are still in the tree:
   `packages/core/src/print/qz.ts:39-50` signs **in the browser** with a private key
   that was shipped to the client (`initPrinting({ signKey })`, and note the file
   `pos/privateKey.d.ts` / `urypos/src/privateKey.js`), whereas
   `ury/ury/api/ury_print.py:237-257` is the newer **server-side sign-only endpoint**
   with the comment *"The private key never leaves the server; these users may only
   ask the server to sign a payload"* (`ury_print.py:202-210`) and a role allowlist.
   There is even a path-traversal guard on reading the key
   (`ury_print.py:227-231`, `os.path.commonpath`). If you take one security lesson
   from this review, take that one.

2. **`network`** — **fully server-side**. The Frappe server renders the doc to a PDF,
   writes it to `/tmp`, and pushes it to a **CUPS** server over the LAN:
   `ury_print.py:34-63`. `cups.setServer(...); conn.printFile(printer_name, file_path, name, {})`,
   with the temp file removed in a `finally` (`:76-78`). The browser is never
   involved. `import cups` is inside a try (`:34-37`) returning the string
   `"Failed to import cups"` — an on-prem deployment detail leaking into an API return
   value. All the KOT printing goes through Frappe's `print_by_server`
   (`ury_kot.py:25`, `ury_waiter_print.py:184-191`, `ury_kot_reprint.py:87`), which is
   the same server-side path.

3. **`socket` / websocket_print** — the one you asked about, and it is much smaller
   than the name suggests. `ury/ury/page/websocket_print/websocket_print.js` is
   **57 lines** and it is a *browser tab acting as a print spooler*:

   ```js
   const print_channel = `print_${branch}`;              // :11
   frappe.realtime.on(print_channel, (data) => {          // :12
       if (!(data.data.name in localStorage)) {           // :13  ← de-dupe
           get_print_html(set_preview, wrapper, data.data.doctype, data.data.name, data.data.print_format)
           localStorage.setItem(data.data.name, '')       // :15
       }
   })
   ```

   and `set_preview` (`:41-57`) builds a **hidden `<iframe>`**, writes the
   server-rendered HTML into it, calls `iframe.contentWindow.print()`, and removes the
   iframe. The server side is four lines: `ury_print.py:182-183` publishes
   `{"data": {name, doctype, print_format}}` on channel `print_{branch}` and returns.

   **What this architecture actually is:** the printer is addressed **not at all**. It
   is whatever the OS print dialog / default printer of *that particular browser tab*
   is. The "address" is the pair (branch channel, whichever machine has the
   websocket-print page open). That is why the de-dupe on line 13 exists — if two
   people leave the page open, both tabs print, and `localStorage` is the only thing
   stopping it. It is per-browser, never cleaned up, and grows unbounded. It also
   means: reload the tab and every past invoice can print again... no — reload keeps
   `localStorage`, but **clear site data and history replays**. And if nobody has the
   tab open, the invoice is marked `invoice_printed = 1` anyway
   (`ury_print.py:185-192`) and the tables are released, because the publish is
   fire-and-forget with no subscriber count.

   What it buys them: **zero install**. No QZ, no Java, no CUPS, no server on the LAN.
   A tablet in the corner with a Chrome tab open is the print station. For a small
   Indian restaurant that is a genuinely rational trade.

**Odoo: two, both with the browser holding the connection.**
`point_of_sale/models/pos_printer.py:35-42` — `printer_type` is either `iot`
(an **IoT Box**: a Raspberry Pi on the LAN acting as a hardware proxy, addressed by
`proxy_ip`, `pos_printer.py:43`) or `epson_epos` (**ePOS-Print**, the printer's own
embedded HTTP/XML server, addressed by `epson_printer_ip`, `:47-54`). Bytes are
produced **in the browser** — the receipt is a DOM tree rendered to an image and
posted to the proxy or the printer.

The Epson path has a piece of real-world scar tissue you would never invent:
`pos_printer.py:9-25`, `format_epson_certified_domain`. Browsers refuse to make
requests to `https://192.168.1.50` because no CA will issue a certificate for a
private IP. Epson's answer is a wildcard cert on `*.omnilinkcert.epson.biz`, where the
subdomain is derived from the printer's serial number. So Odoo takes the serial,
SHA-256s it, base32-encodes it, lowercases it, strips `=` padding, and appends the
domain — and the `onchange` (`:77-81`) silently rewrites whatever the installer typed
into that hostname. The guard at `:16-19` is "if it contains a dot it's already an IP
or a hostname, leave it alone." There's also an admin-facing
`use_local_network_access` toggle (`:64-69`) for Chrome's Private Network Access
permission prompt. **This whole function exists because a browser cannot talk to a
device on the local network over HTTPS.** Any design where the browser is directly on
the wire with the printer inherits this problem.

## 6. Things we would not have thought of

- **Printing the bill is what frees the table.** `ury_print.py:69-71` and `:190-192`
  call `release_merge_cluster_tables(restaurant_table)` on the transition
  `invoice_printed 0 → 1`, guarded so it fires exactly once. The whole floor state
  machine hangs off a print.
- **"Block takeaway KOT" per printer.** `custom_block_takeaway_kot` on a production
  unit's printer row (`ury_kot.py:50-52`): this printer prints only for real tables,
  never for parcels. A station whose printer is behind the hot line shouldn't be
  spitting out delivery tickets that the packing counter handles.
- **A takeaway *table*.** `URY Table.is_take_away` (`ury_waiter_print.py:22-25`) — a
  pseudo-table for parcels, and `_is_takeaway_table` returns `True` for *no table at
  all* too. The waiter slip is suppressed for both (`ury_waiter_print.py:161-162`):
  no waiter, no slip.
- **One combined waiter slip per order update, spanning stations.** The kitchen gets
  N tickets (one per station); the waiter gets **one** slip that aggregates all of
  them — `ury_kot_generate.py:404-405` collects every KOT name created in this
  submit and `ury_waiter_print.py:108-127` builds a synthetic combined doc via
  `frappe.copy_doc` and prints it with `doc=combined_doc` (an unsaved document handed
  to the print engine). Additions first, cancellations after
  (`ury_waiter_print.py:55`).
- **Course firing as a print event with no items on it.** Odoo's
  `printCourseTicket` (`pos_store.js:1023-1038`) prints a ticket whose `new` and
  `cancelled` are both empty and whose `noteUpdate` is just the course's product ids,
  with `noteUpdateTitle: "Course 2 fired"` and `printNoteUpdateData: false` — a
  header-and-names-only "start the mains now" slip. The whole call is inside a
  try/catch that only logs (`:1033-1037`): failing to print the fire slip must not
  fail the fire.
- **The first course auto-fires on first send.** `pos_store.js:136-147`: sending an
  order to preparation marks course 1 `fired` if it isn't already, but **not** on a
  cancellation (`if (!opts.cancelled)`). Cancelling a round must not start the next one.
- **Adding a line auto-creates course 2.** `pos_store.js:996-1007` — the moment an
  order gets courses, existing lines go to course 1 and an *empty* course 2 is
  created and selected, so the next thing the waiter taps lands in the next course
  without them thinking about it.
- **"You haven't sent this order" on the way to payment.** `_askForPreparation`
  (`pos_store.js:616-638`) intercepts `pay()` (`:639-642`): if there are undiffed
  changes, a modal offers to send them first, and the UI is `block()`ed during the
  send (`:632-635`). The most common real-world bug — guest pays, kitchen never got
  the last item — is caught at the till.
- **A per-round summary toast in the waiter's language.** `pos_store.js:109-124`
  tells the waiter *"3 Starters, 2 Drinks, sent to the kitchen"* using
  `formatList` (locale-correct "and"/"och"/"et"), built from the diff, not from the
  order.
- **Idle timeout bounces back to the floor plan after 3 minutes** —
  `pos_store.js:51-65`, excluding PaymentScreen/TicketScreen/LoginScreen. A tablet
  left on a table doesn't sit on someone's open order.
- **Notification storm suppression.** URY's delayed-order alert refuses to create a
  `Notification Log` if an identical subject went to the same user in the last
  5 minutes — `ury/ury/api/ury_kot_notification.py:72-81`.
- **Audio alert with a last-KOT-time echo guard.** The KDS push carries
  `audio_file` and `last_kot_time` from a Redis cache key
  `{branch}_{production}_last_kot_time` (`ury_kot.py:100-110`), and the client only
  chimes when the time differs (`mosaic/src/components/kot.vue:619-628`) — otherwise
  a reconnect replays the sound.
- **Order-type filtering on the KDS, independent of printing.**
  `ury_kot.py:91-97`: a production unit can be configured to only *display* certain
  order types (dine-in but not aggregator), and the ticket is still printed and still
  exists — it just doesn't appear on that screen.
- **Reprint is a permission, not a button.** `ury_kot_reprint.py:42-47` — only the
  captain who owns the order, or elevated access. Billing access explicitly does
  **not** grant reprint, and the comment says so.
- **"Pro forma receipt" is the same template with a banner.**
  `pos_restaurant/.../order_receipt/order_receipt.xml:6` —
  `t-if="!order.finalized"`. Odoo prints the pre-payment bill from the identical
  receipt template, stamped, so the two can never drift.
- **Printed ⇒ payment frozen.** `point_of_sale/models/pos_order.py:623-624`:
  *"You cannot change the payment of a printed order."*
- **The `noteUpdate` bucket also carries a title and a data-suppression flag**
  (`noteUpdateTitle`, `printNoteUpdateData` — `pos_store.js:1029-1030`). Their
  "print something informational at the kitchen" primitive is deliberately general.

## What I would steal, ranked

1. **Odoo's persisted last-printed snapshot + client-side diff, with a server-side
   staleness guard.** `pos_order.py:305` and `:396-416`. It is the only design in
   either donor that survives two tablets, a merge, and a reconnect. The specific
   thing to copy is the `metadata.serverDate` comparison and its stated bias: when in
   doubt, keep the server's snapshot and risk a duplicate, never accept a stale one
   and risk a lost dish.
2. **Separate "cancelled" tickets that back-link to the original ticket, and print
   `old -> new` rather than a delta.** `ury_kot_generate.py:271-287` and
   `ury_waiter_print.py:82-101`. A cook holding a rail of tickets needs to find the
   one to amend; a bare "-2" doesn't help them.
3. **SambaPOS's `Locked` flag as a business rule, not a data structure.**
   `Ticket.cs:487-491`. Whatever our diff representation is, the rule
   *"a line the kitchen has seen cannot be silently deleted, only voided"* must be a
   guard clause, not a convention.
4. **The every-minute reconciler that finds orders with no ticket, prints a
   `Duplicate`, and logs it.** `ury_kot_validation.py:12-36` plus the 1-minute grace
   window. This is the answer to "how do you know it printed" when you refuse to build
   a printer status model — and refusing to build one is the right call.
5. **The `_askForPreparation` modal on the way to payment.**
   `pos_store.js:616-642`. One dialog that catches the single most expensive
   real-world mistake.
6. **The per-shift human order number, with a separate aggregator counter and
   prefix.** `ury_kot_order_number.py:18-28`. Kitchen staff cannot read
   `ACC-PSINV-2026-00042871` aloud, and a Swiggy ticket must look different from
   table 6's.
7. **Server-side-only signing for any local print agent.** `ury_print.py:202-257`
   including the `os.path.commonpath` traversal guard and the role allowlist. Take the
   fixed version, not `packages/core/src/print/qz.ts:39-50`.
8. **`noteUpdate` as a first-class change type.** `pos_store.js:504-512`. A note
   edit with no quantity change is a real event and URY's diff misses it entirely
   (`ury_kot_generate.py:409-423`) — that is the bug to not repeat.
9. **Pro-forma bill = the final receipt template plus a banner.**
   `order_receipt.xml:6`. Two templates always drift; one never does.
10. **Printer-role checkboxes on one row (`bill` / `kot_print` / `waiter_print`)
    rather than three printer lists.** `ury/ury/custom/ury_printer_settings.json`.
    It models "this one printer does two jobs" without a join table.

## What I would not steal

- **URY's `except: pass` around kitchen printing** (`ury_kot.py:22-27`). Not a design,
  a wound. Every print attempt needs a persisted outcome row.
- **URY's `msgprint` for an unmapped product** (`ury_kot_generate.py:138-140`). A toast
  that the cashier dismisses while the dish evaporates. If nothing routes, the send
  must fail loudly or fall back to a default printer — and the "no printers on the
  production unit prints nowhere" indentation bug at `ury_kot.py:47-83` is the same
  failure by accident.
- **URY's item_code-only diff** (`ury_kot_generate.py:409-423`). We have per-line
  identity in the cart; use it. Their own display layer already keys on
  `(item, comments)` (`ury_waiter_print.py:34`), which shows they knew.
- **Odoo's Epson certificate-domain derivation** (`pos_printer.py:9-25`) and the whole
  browser-talks-to-printer-over-HTTPS problem it solves. Only worth inheriting if the
  browser is directly on the wire. If the print path is server-side or via an agent,
  this is 20 lines of somebody else's pain.
- **URY's CUPS path** (`ury_print.py:34-63`). It assumes a machine on the restaurant's
  LAN that is always up and runs Python with pycups. That is an on-prem-server shape.
  Ours is Firebase; there is no such machine.
- **The `websocket_print` browser-tab-as-spooler** (`websocket_print.js`), *as the
  primary path*. `localStorage` as a de-dupe store is per-browser, unbounded, and
  silently useless if the tab is closed — the invoice gets marked printed and the
  tables get released regardless (`ury_print.py:185-192`). It is worth knowing as an
  emergency fallback precisely because it needs zero install, but it must never be
  the thing that marks a bill printed.
- **Odoo's `uiState.lastPrints` living in client UI state.** Merging two orders has to
  hand-merge two print histories (`pos_store.js:263-288`) and hand-move snapshot
  quantities (`:148-172`) because the history isn't a server-side append-only log.
  A server-side ticket log makes both of those functions disappear.
- **Blocking bill reprint entirely** (`pos_print.js:50-56`). Correct instinct
  (a second bill is a fraud vector), wrong mechanism — the right answer is a
  reprint that is allowed, marked **REPRINT** on the paper, and audited, which is
  exactly what URY does for KOTs (`ury_kot_reprint.py:42-71`) and not for bills.

## Where Odoo and URY disagree

| | **Odoo** | **URY** |
|---|---|---|
| **Routing key** | POS category (customer-facing), many-to-many to printer (`pos_printer.py:44`); only the first category is used for the summary (`pos_store.js:491`) | `Item.item_group` → Production Unit (a station) → printers; three-tier fallback unit→room→profile (`ury_kot.py:38-83`) |
| **Who diffs** | The client, against a server-persisted snapshot (`pos_order.py:305`) | The server, against a before-array the client posts (`ury_kot_generate.py:336-356`) |
| **Line identity** | `preparationKey` — composite, uuid-based (`pos_store.js:149`, `pos_session.py:27`) | `item_code` only (`ury_kot_generate.py:414`) |
| **Cancellation** | A bucket inside the same diff ticket (`pos_store.js:264-266`) | A separate document, separate `CNCL-` series, back-linked to the original KOT (`ury_kot_generate.py:271-292`) |
| **Cancellation display** | The `cancelled` list | `old -> new` in red (`ury_waiter_print.py:86-88`, `ury_waiter_order_slip.json`) |
| **Note-only change** | First-class `noteUpdate` ticket (`pos_store.js:504-512`) | Invisible — no diff is produced |
| **Multi-station order** | One ticket per printer, filtered client-side | One KOT *document* per station, plus one combined waiter slip (`ury_waiter_print.py:156-196`) |
| **Print failure** | No status query; state advances on believed success | Kitchen: swallowed (`ury_kot.py:26`). Bill: acked, and the ack releases tables (`ury_print.py:69-71`) |
| **Missed ticket** | Detected by the UI ("order not sent" modal at `pos_store.js:616-638`) | Detected by a cron reconciler that prints a `Duplicate` (`ury_kot_validation.py:12-36`) |
| **Reprint** | Reprints the last diff, button only shown when a print exists (`actionpad_widget.xml:50-56`) | Feature-flagged, ownership-gated, and re-resolves the printer from scratch — may print elsewhere (`ury_kot_reprint.py:62-71`) |
| **Where bytes are made** | Browser DOM → IoT Box proxy or Epson ePOS (`pos_printer.py:35-54`) | Server-rendered HTML/PDF → QZ agent, CUPS, or a browser tab (`pos/src/lib/print.ts:16-42`) |
| **Course firing** | Explicit `restaurant.order.course` model with `fired`/`fired_date`, and a fire ticket (`restaurant_order_course.py:12-29`, `pos_store.js:1011-1038`) | `course` is a string copied onto each KOT item from the menu (`ury_kot_generate.py:72`); no firing |
| **Guest count** | Prompted for, summed on merge, printed on the kitchen ticket (`pos_store.js:222-223`, `order_change_receipt_template.xml:6-8`) | `no_of_pax` on the bill only |

The disagreement that matters most is **line identity**. Odoo keys the printed
snapshot on a composite per-line key and therefore can express "this specific line's
note changed" and "these 2 of 5 were cancelled"; URY keys on item_code and therefore
cannot, which is why a comment edit vanishes and why two differently-commented lines
of the same dish collapse. Everything else in the table is a consequence.

The second is **where the diff runs**. URY's server-side diff means a tablet that
reconnects with a stale `previous_items` will re-print the whole order; Odoo's
`serverDate` guard (`pos_order.py:408-416`) is exactly the defence URY never built.
But URY's version needs no persisted snapshot and no merge-time snapshot surgery.
The honest read is that Odoo paid for correctness with `handlePreparationHistory`
(`pos_store.js:148-172`) and the merge code around it — roughly 150 lines that exist
only because the snapshot is a mutable blob rather than an append-only server log.
