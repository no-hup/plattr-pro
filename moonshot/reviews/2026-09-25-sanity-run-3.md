### S3-1 · P3 · Kitchen and waiter screens name the table by its raw id, "tbl_meg_6"

*Scene.* 20:05. Table 6 orders Chicken 65. The kitchen ticket's header reads "tbl_meg_6". The
waiter's card reads "Table tbl_meg_6", and so do the serve dialog, the order detail and the Tables tab.
Nobody in the restaurant calls it that.

*Steps from a clean seed.* Re-import MockData7. Check out one dish on `tbl_meg_6` (guest app, or
`floorstate.mjs 6 ordered`). Log in to the kitchen app as `kitchen@meg.test` and read card
`kitchen-cart-<orderId>_0`. Log in to the server app as `server@meg.test` and read `order-cart-<cartId>`.

*Expected.* The table's number or name ("6"). The till floor and the bill already say "6".

*Seen.* Kitchen: "tbl_meg_6 1m 1x Chicken 65 #0 PENDING". Waiter: "Table tbl_meg_6 READY 1× Chicken
65 #LMbA7 ₹280" and "Mark this cart from Table tbl_meg_6 as served?". Both read APIs send
`tableId: "tbl_meg_6"` and no table number.

*Evidence.* Trajectory hops 2, 3 and 7.

*Where to look.* [TD-046](../TECH_DEBT.md) says the kitchen read puts a `ticketLabel` under
`tableId`. No `ticketLabel` exists anywhere in `backend/src-plattr/functions` or the Flutter apps
(`git log -S ticketLabel` on the backend is empty), so TD-046 describes an alias that was never built.

### S3-5 · P3 · The waiter's order detail shows impossible dates

*Seen.* "Created: 1970-01-01T05:30:00.000", "Updated: +058702-06-27T11:34:39.000", and each cart's
"Checkout: 2026-09-25T02:41:27.539Z" as a raw ISO string. The order also reads "Order
#FD9BChgATbNdpB2ST0Ya" (the document id) and "Server: Unassigned" after this waiter served it.

*Steps.* Server app, tap any order card (a plain tap opens the detail).

*Caveat.* On the emulator, `createdAt` arrives as a `{_seconds,_nanoseconds}` map and `updatedAt` as
epoch-ms, both from the `utils/timestamp.js` fallback. A callable also serialises a real prod
Timestamp as `{_seconds,…}`, so "1970" probably happens in prod too. That isn't verified.

*Evidence.* Trajectory hop 13.

*Where to look.* `platter_server/lib/pages/orders_home/order_detail_screen.dart:187`, and the model
that parses `createdAt` / `updatedAt`.

## Notes (not filed as bugs)

- **Empty Served tab on the emulator.** `getServedCartsForServer` queries `updatedAt >= <Date>`.
  `markCartAsServed` writes `updatedAt` with `timestamp.now()`, which on the emulator falls back to
  `Date.now()` (a number). Firestore orders numbers before timestamps, so no served cart from the run
  ever matches, and only seeded orders with a real Timestamp show. It's the known emulator-sentinel
  gotcha, not a finding. It is now in [AGENT_QA.md](../../AGENT_QA.md) §8.
- **Kitchen Mark Ready is recorded as `userId: "system"`,** while the waiter's Serve records
  `srv_meg_1`. If the kitchen's act is meant to be attributable, it isn't.
- **No Preparing step in the kitchen UI.** The sheet goes straight from PENDING to Mark Ready, and the
  backend accepts PENDING → READY. That's by design as far as this run can tell.
- **Kitchen History tab** is a stub: "History coming soon. Kitchen history is not yet wired to the
  backend." It's honest, but it isn't in TECH_DEBT.
- **"Mark Served" stays on a served cart** on the order detail ("Cart 2 SERVED … Mark Served"). A tap
  fires nothing. It's P3 wording, left out of the findings.
- **The waiter can "Mark Paid" from the order detail** (`order-mark-paid`). That is the second payment
  writer covered by TD-010. Not exercised.
- **Known, confirmed present:** TD-082 (step 7). TD-046 was touched by S3-1.
- **Environment noise:** a client this run didn't start polled `order-getActiveCartsForKitchen` with a
  dead session (`tYvFcfQWOnqwANHbzr1G`) throughout, the same as in run 2. It was told apart by the
  session id.
