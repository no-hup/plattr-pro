## 1. Opening a ticket with no customer identity

**Odoo.** The order is created with `partner_id` simply left false. There is no
requirement anywhere that a POS order have a customer; `partner_id` is an ordinary
optional m2o (`point_of_sale/models/pos_order.py:325`). What the order *must* have is a
session: `_process_order` browses `order['session_id']` first thing
(`pos_order.py:70`), and `create()` runs `_complete_values_from_session`
(`pos_order.py:563-568`) which fills pricelist, fiscal position, company, preset,
`pos_reference` and `tracking_number` from the config
(`pos_order.py:582-597`). The customer-facing receipt number and the short kitchen
"order number" are both minted server-side there, not by the client:
`pos_config._get_next_order_refs()` returns `"{yy}{device}-{config}-{seq}"` plus a
`tracking_number` that is `seq % 1000` — a 3-digit number that wraps. A `uuid` generated
client-side is the real identity and it carries a DB unique constraint
(`pos_order.py:369`, `pos_order.py:388`).

The dine-in / takeaway distinction in Odoo is **two orthogonal things, neither of them a
type field**:

- `table_id` (`pos_restaurant/models/pos_order.py:8`) — nullable m2o to
  `restaurant.table`. Present = dine-in. Absent = not at a table.
- `preset_id` (`point_of_sale/models/pos_order.py:345`) — a `pos.preset` record, which is
  a *bundle of config* (pricelist, fiscal position, whether identification is required,
  whether it is a return, timing/slots) rather than a type. The restaurant module ships
  exactly three seeded presets, "Take in / Takeout / Delivery", and refuses to let you
  delete them (`pos_restaurant/models/pos_preset.py:14-22`).
- `floating_order_name` (`pos_order.py:346`) — the free-text label for a counter ticket
  with no table ("John", "blue jacket").

So a counter ticket is *an order with no table and a name*, and `test_direct_sales`
asserts the fallback: if the client syncs an order with neither `table_id` nor
`floating_order_name`, the server stuffs the `tracking_number` into
`floating_order_name` so the ticket is never anonymous on screen
(`pos_restaurant/tests/test_frontend.py:855-865`).

Guest count is its own field, `customer_count` (`pos_restaurant/models/pos_order.py:9`),
and defaults to the *table's* `seats` unless a preset forces the cashier to enter it
(`pos_preset.use_guest`, `pos_restaurant/models/pos_preset.py:8`; test at
`test_frontend.py:666-679`).

**URY.** The opposite: the customer is **mandatory**. `sync_order` throws
`"Please enter valid customer details"` if none is passed
(`ury/ury/doctype/ury_order/ury_order.py:1437-1440`), and a POS Invoice validate hook
throws again if `customer_name` is empty
(`ury/ury/hooks/ury_pos_invoice.py:80-86`). The walk-in is handled by pointing that
mandatory field at a house customer — the self-ordering profile has a
`default_customer` field and falls back to it
(`ury/ury/api/self_ordering.py:600-602`). That is the Indian-restaurant shape: every bill
has a party on it for GST, and "Walk-in Customer" is a real Customer record.

URY's document is an ERPNext **POS Invoice in draft** (`docstatus=0`). There is no
separate "order" document at all — the running tab *is* a draft tax invoice. Opening a
ticket is `_resolve_or_create_pos_invoice` (`ury_order.py:690-831`): look for a draft
invoice on this table, else `frappe.new_doc("POS Invoice")` with `is_pos=1`,
`update_stock=1`, naming series from the restaurant, tax template from the restaurant,
price list from the room's menu.

URY's order kind **is** a first-class field, `order_type` ∈ {`Dine In`, `Take Away`,
`Aggregators`, `Shopping Cart`}. And here is the nice trick: **takeaway is modelled as a
pseudo-table.** `URY Table` has an `is_take_away` flag, and the order type is derived
from it, not chosen (`ury_order.py:771-775`, and again defensively in a before_insert
hook at `ury/ury/hooks/ury_pos_invoice.py:138-147`). So a counter order is "table
COUNTER-1", and the whole table machinery (occupied flag, cluster, release) works
unchanged. A pickup order with no table at all gets `order_type` derived from the absence
of a table instead (`ury/ury/api/self_ordering.py:371`, `:564`) — and a comment there
records that this was a live bug: pickup invoices were saving with an **empty**
`order_type` because `_resolve_or_create_pos_invoice` only derives it from the table
(`self_ordering.py:589-597`).

**Dolibarr TakePOS** is the cheapest model of the four and worth knowing about. A "place"
(table) is not a foreign key — it is baked into the draft invoice's **ref string**:
`(PROV-POS<terminal>-<place>)`. Opening table 7 means fetching an invoice by that ref
(`dolibarr/invoice.php:222`) and creating one with that ref if absent
(`invoice.php:795-798`). Place `0` is the counter, and counter tickets are `0-1`, `0-2`, …
(`invoice.php:1880`, `:1894`). "Is the table occupied?" is not stored anywhere: the floor
plan asks, for each table, *does a draft invoice with that ref exist*
(`dolibarr/floors.php:84-94`). Zero denormalised state, therefore zero drift.

**SambaPOS** generalises hardest. A ticket has a list of `TicketEntity` rows
(`samba/Ticket.cs:134-138`, `samba/TicketEntity.cs`) — an entity is *anything*: the table,
the customer, the delivery driver, the room. Assigning a table is
`UpdateEntity(entityTypeId, entityId, …)`, and passing `entityId == 0` removes it
(`Ticket.cs:620-645`). There is no table field and no order type; "dine-in" is just
"a ticket that has an entity of type Table attached". Notably `CanCloseTicket()` returns
true if the remaining amount is zero **or the ticket has any entity attached** or it is
empty (`Ticket.cs:758-761`) — i.e. an unpaid ticket can be parked precisely because it is
attached to a table, and a walk-in ticket with nothing attached cannot be parked at all.

## 2. Takeaway and phone orders — how far does the branching spread?

**Odoo: it barely branches at all.** `preset_id` is data, not a code path. Grepping the
backend, the only places the preset matters are (a) defaults copied at create
(`pos_order.py:586-587`), (b) `preset_time` for scheduled orders, and (c) the one real
behavioural difference: **a scheduled order survives day close**. `close_session_from_ui`
finds draft orders whose `preset_time` is in the future and *detaches them from the
session* — `future_orders.session_id = False` — so they are not blockers and are not
cancelled (`point_of_sale/models/pos_session.py:619-624`). `get_session_orders()` likewise
only counts orders with no preset time or a past one (`pos_session.py:382-386`). Tests
lock this: `test_close_with_planned_order_later_today` asserts the session closes, the
order stays `draft`, and its `session_id` is now false
(`pos_restaurant/tests/test_frontend.py:713-744`). Cancelling a future order is also
refused outright (`pos_order.py:1243-1245`). Billing and reporting do not branch on
preset at all.

**URY: it branches in eight or nine places, and that is the warning.** `order_type ==
"Aggregators"` (Swiggy/Zomato) changes: the naming series
(`ury/ury/hooks/ury_pos_invoice.py:131-134`), the price list (a per-aggregator price list
that throws if unconfigured — `ury_order.py:1501-1505` and
`ury/ury/hooks/ury_pos_invoice.py:176-185`), whether taxes are applied at all
(`ury/ury/hooks/ury_sales_invoice.py:54-60`), the KOT token-number series (`AGR - 1`
vs `1`, `ury/ury/api/ury_kot_order_number.py:6-96`), whether the KOT shows on a given
kitchen display (`ury/ury/api/ury_kot_display.py:151-159`), and the KOT document itself
(`ury/ury/api/ury_kot_generate.py:43`, `:260`). And `order_type != "Dine In"` is the guard
that stops table release from firing for a takeaway ticket
(`ury/ury/hooks/ury_pos_invoice.py:318-322`). The dashboard has to backfill a default
because old invoices have no `order_type` at all (`ury/ury/api/dashboard.py:50-51`).

That spread is the cost of making order kind a first-class enum. It is worth it for the
aggregator case (genuinely different tax, price and token rules) and *not* worth it for
takeaway-vs-dine-in, which URY handles fine as a pseudo-table.

## 3. Table operations — move, merge, split

### Move (transfer)

**URY, `table_transfer(table, newTable, invoice)` — `ury_order.py:1719-1774`.** The whole
transaction, in order:

1. `frappe.has_permission("POS Invoice", "write")` on the invoice (`:1725`).
2. The invoice must have a POS Profile, else refuse — you cannot check transfer rights
   without one (`:1731-1735`).
3. The acting user's roles must intersect the profile's `transfer_role_permissions`
   (`:1738-1742`). The comment above it is explicit that the frontend's
   `canCaptainTransfer()` is UX only and must not be trusted.
4. **Refuse if the source table is merged**: `_get_merge_cluster(table)` and if
   `len(members) > 1`, `"Table transfer is not allowed for merged tables. Unmerge
   first."` (`:1744-1746`).
5. Refuse across branches (`:1748-1749`).
6. Refuse if the destination is occupied (`:1751-1752`).
7. Then mutate, in this order: **destination table → occupied=1** with the invoice's
   original `creation` timestamp as `latest_invoice_time` (so the party keeps its seated
   clock — nice touch), **source table → occupied=0, timer null**, then the invoice's
   `restaurant_table` and `custom_restaurant_room`, then `save()` (`:1754-1767`).
8. Finally, re-stamp the live KOTs: `change_table_in_kot` updates `restaurant_table` on
   every KOT for this invoice that is `docstatus=1`, `order_status="Ready For Prepare"`
   and `verified=0`, and publishes a realtime event per production unit so the kitchen
   screen redraws (`ury_order.py:2156-2173`). **Already-cooked KOTs are deliberately not
   re-stamped** — only the ones still waiting. This whole step is wrapped in a bare
   `try/except: pass` (`:1769-1774`): a KOT app failure must not roll back the transfer.

Note the ordering hazard: the table flags are written with `frappe.db.set_value` *before*
`pos_invoice.save()`. If the save throws, the tables are already flipped. There is no
explicit transaction around it.

**Odoo.** I could not find a server-side table-transfer function. Transfer is a
client-side operation that rewrites `table_id` on the in-memory order and re-syncs; the
only backend trace is the tour test `test_transfering_orders`
(`pos_restaurant/tests/test_frontend.py:849-853`) and the fact that
`_get_open_order` resolves an order by **either uuid or (table_id, draft, config)**
(`pos_restaurant/models/pos_order.py:17-22`) — meaning the *table* is an identity for the
open ticket, not just a label. So "move to table 12" and "open table 12" are the same
lookup, and two devices doing both at once converge on one order.

### Merge

**Odoo's merge is a floor-plan operation, not an order operation.** `restaurant.table` has
`parent_id` (`pos_restaurant/models/pos_restaurant.py:107`), and merging is
`set_parent_id(parent_id, config_id)` (`:140-150`), which does exactly one interesting
thing: it sets the parent, then calls `self._has_cycle('parent_id')` and **rolls the
assignment back** if a cycle would be created. No error, no message — it just silently
keeps the old parent. `test_table_parent_circular_relation_is_rejected`
(`pos_restaurant/tests/test_pos_restaurant_flow.py:11-39`) pins the behaviour: B→A
succeeds, A→B is silently ignored, B keeps A. The orders then follow the parent chain on
the client. The one backend trace of merging orders is
`test_tax_in_merge_table_order_line` (`test_frontend.py:536-561`), which exists because
merging two tables' orders once lost the tax on the destination's lines.

**URY's merge is a real transaction** — `merge_tables_batch(anchor_table, tables)`,
`ury_order.py:26-141`:

1. Dedupe targets, drop the anchor itself; refuse if empty (`:32-43`).
2. Read the anchor's room; refuse if the table does not exist (`:45-54`).
3. Build the anchor's existing cluster via BFS over the symmetric `merged_with` CSV
   (`_get_merge_cluster`, `:241-275`).
4. Per target: refuse if it is in a **different room** (`:71-74`); refuse if it is
   **already part of a merged group** — you cannot merge a merged group into another
   (`:81-86`); refuse if it is **occupied** (`:95-98`).
5. Refuse if the resulting cluster would contain **more than one table with its own
   active order** (`_count_separate_active_orders`, `:102-107`). Active = a POS Invoice
   with `docstatus=0` and `invoice_printed=0` (`:224-234`).
6. Write `merged_with` symmetrically on every member — each row stores the CSV of *the
   others* (`:112-128`).
7. `_sync_active_order_with_merge_cluster` (`:158-216`): find the cluster's open unprinted
   invoices, pick the **oldest by `creation`** as primary, write the other member names
   into the primary's `custom_merged_tables`, and mark every member `occupied=1` with the
   primary's creation time.
8. `_reconcile_open_invoices_for_tables` (`:350-358`) re-derives `custom_merged_tables`
   on every open invoice touching any of these tables, from the live table graph.
9. `frappe.db.commit()`.

The shape to notice: **the table graph is the source of truth, the invoice's
`custom_merged_tables` is a cache**, and there is a dedicated reconciler
(`_reconcile_invoice_merged_tables`, `:306-330`) that re-derives the cache from the graph
and is called on every read (`:786`), on every write (`:1499`) and after every merge. They
have clearly been burnt by the two drifting apart.

### Split

**URY `split_bill(source_invoice, items_to_move, customer)` — `ury_order.py:544-686`.**
Refuses unless the source is `docstatus == 0` (`:566-567`), unless the caller has write
permission (`:552-553`), and unless the caller's branch matches (`:563-564`). Then:
refuse to move more than a line's qty (`:581-584`), refuse if nothing moves (`:588-589`),
and — the one I like — **refuse if nothing would remain on the original bill**
(`:590-591`). A split that empties the source is a rename, not a split, and they will not
let you do it that way.

The new invoice copies 21 header fields explicitly (`:594-619`) — including
`restaurant_table` and `custom_merged_tables`, so both halves stay attached to the same
table. Both halves get the same `custom_split_group` hash and the child gets
`custom_split_from` (`:621-627`). Partial moves decrement the source line's qty in place;
full moves remove the line (`:635-647`). A `frappe.flags.ury_bill_split` flag is set for
the duration (`:651`, `:681`) because two hooks have to stand down during a split:
`validate_invoice`'s "you cannot remove items after printing" check
(`ury/ury/hooks/ury_pos_invoice.py:32-33`) and `restrict_existing_order`'s "this table
already has an invoice" check (`ury/ury/hooks/ury_pos_invoice.py:199-200`, with an
explicit second escape at `:202-214` for the split child).

**Dolibarr's split is one UPDATE.** `UPDATE facturedet SET fk_facture = <split invoice>
WHERE rowid = <line>` (`dolibarr/split.php:97-98`) — the line is simply reparented to a
scratch invoice whose ref is `(PROV-POS<term>-SPLIT)`, created lazily. Unsplit moves it
back to `(PROV-POS<term>-<place>)` (`split.php:99-130`), with one guard: if you are
already on the SPLIT place, rewrite it to `0` so you cannot move a line to the place it is
already on (`split.php:101-103`).

**SambaPOS** merges *lines*, not tables. `OrderMerger.CanMergeOrders` is the definitive
list of what makes two lines "the same line"
(`samba/OrderMerger.cs:65-77`): same quantity, same price, same menu item, same portion,
same `CalculatePrice`, same `IncreaseInventory`, same `DecreaseInventory`, **no order tags
on either side**, and equal order-state sets (`:79-86`). Any modifier at all and the lines
stay separate. Lines with `Quantity > 1` are excluded from merging up front
(`OrderMerger.cs:13-15`).

### What will not move, and what happens to a sent line

- **URY: a merged table cannot be transferred.** Unmerge first (`ury_order.py:1745-1746`).
- **URY: an occupied table cannot be merged in** (`:95-98`), and **two tables with their
  own live orders cannot be merged** (`:102-107`). They will not attempt to fuse two
  tickets.
- **URY: a printed bill cannot be modified** by a non-billing user
  (`ury_order.py:1344-1348`), and a hook re-checks it at validate time against the stored
  document, comparing per-item quantities and naming exactly which items were removed or
  reduced (`ury/ury/hooks/ury_pos_invoice.py:34-77`). This is gated by a POS Profile flag
  `remove_items`.
- **URY: printing is mandatory before submitting a dine-in bill** —
  `validate_invoice_print` throws "Printing the invoice is mandatory before submitting"
  whenever `restaurant_table` is set and `invoice_printed == 0`
  (`ury/ury/hooks/ury_pos_invoice.py:106-114`).
- **Odoo: a paid order cannot go back to draft.** `write()` raises if you try to move a
  state out of {paid, done, invoiced} (`pos_order.py:609-611`).
- **Odoo: you cannot change the payment of a printed order** — `nb_print > 0` plus any
  non-cancelled payment command raises (`pos_order.py:623-624`).
- **Odoo: order lines can only be deleted while the order is draft or cancel**
  (`pos_order.py:1788-1791`); orders themselves likewise
  (`pos_order.py:551-561`).
- **Dolibarr: a line that has been sent to the kitchen is marked `special_code='4'`**
  (`dolibarr/invoice.php:1444`), and editing or deleting it requires the *separate*
  `takepos->editorderedlines` permission on top of `editlines`
  (`invoice.php:1184`). That is the cleanest expression of "printed lines are a different
  privilege" I found in any donor.

## 4. Un-merging

**URY, `unmerge_tables(table)` — `ury_order.py:461-491`.** Refuse if the cluster is size 1
("Table is not merged"). Refuse if **any** table in the cluster has an open unprinted
invoice — `"Cannot unmerge active tables."` (`:473-478`). Otherwise clear `merged_with`
on every member. Note: it is **all or nothing**. There is no "release table 3 of the
three". You unmerge the whole cluster or none of it, and only when the party has gone.

Un-merge is **both** manual and automatic, but the automatic path is a *release*, not an
un-merge, and the distinction matters:

- `release_tables_after_print(invoice)` (`:385-414`) sets `occupied=0` and clears the
  timer on every member — but **leaves `merged_with` intact**. The party has been billed;
  the tables are free; the physical merge stands.
- `release_merge_cluster_tables(...)` (`:361-383`) uses `TABLE_RELEASE_FIELDS`, which
  *does* include `"merged_with": None` — full teardown. Called on cancel
  (`:1909-1911`) and on invoice trash (`ury/ury/hooks/ury_pos_invoice.py:117-119`).
- `_free_tables_if_no_open_invoices(...)` (`:508-524`) is the one on the payment path: it
  only releases **if no open invoice remains anywhere in the group** (`:521-522`). Called
  at the end of `make_invoice` (`:2094-2098`), and if the settled invoice is a secondary
  merged bill it first hops to the primary that actually owns the tables
  (`:2085-2092`).

So: settling one of two split bills on a merged cluster does **not** free the tables. Good.

**The bill of a merged cluster** is one primary POS Invoice carrying
`custom_merged_tables` as a CSV; the other tables have no invoice of their own. Lookups
therefore have to search both ways: `or_filters = {"restaurant_table": table,
"custom_merged_tables": ["like", f"%{table}%"]}` (`ury_order.py:734-739`, and again at
`:341-346`, `:441-451`). That `LIKE %table%` is a real weakness — table `T-1` matches
`T-10`, `T-11`, `T-12`. Do not copy the CSV.

**Odoo.** Un-merge is `set_parent_id` with a falsy parent, i.e. nothing happens at all
(`pos_restaurant/models/pos_restaurant.py:143` guards `if parent_id:`, so passing 0 is a
no-op). I could not find any server-side un-merge or any rule tying un-merge to payment.
It is client state.

## 5. Modifying an order after it has been sent

**Odoo keeps a printed snapshot and diffs against it.** `pos.order` carries
`last_order_preparation_change`, a JSON blob described as "Last printed state of the
order" (`pos_order.py:305`). The client diffs the current lines against it to decide what
to print as an add/void slip; the restaurant module builds one line entry per
`orderline.uuid` with name, note, product, quantity and attribute values
(`pos_restaurant/models/pos_session.py:22-34`).

The interesting part is the conflict resolution. `_ensure_to_keep_last_preparation_change`
(`pos_order.py:396-416`) compares the `metadata.serverDate` on the stored blob against the
one the client is trying to write. If the server's is **newer**, the client's write is
discarded with a warning — *"Preparation changes were outdated, probably linked to a
synching issue."* Otherwise the server re-stamps `serverDate` to now. This is a
last-writer-loses guard specifically so that a laggy tablet cannot resurrect a stale idea
of what the kitchen has seen and cause a double-print. It is called on every sync of an
existing draft (`pos_order.py:1298`) and even on the "sync ignored" path
(`pos_order.py:1307`).

Odoo's audit trail is opt-in per config, `order_edit_tracking`:

- Reducing a line's qty sets `is_edited = True` on the line and posts a chatter message
  `"<product>: Ordered quantity: <old>→<new>"` (`pos_order.py:1740-1746`). Note it only
  fires on a **decrease**, never an increase.
- Deleting a line sets `has_deleted_line = True` on the order and posts
  `"<product>: Deleted line (quantity: N)"` (`pos_order.py:2027-2034`).
- `has_deleted_line` is **write-once** — `write()` strips the key from the vals if the
  flag is already set, so a client can never clear it (`pos_order.py:607-608`).
- `is_edited` on the order is computed from those two (`pos_order.py:541-544`).
- Separately and unconditionally, every payment add/change/remove is turned into an
  English chatter line and posted (`_create_pm_change_log`, `pos_order.py:635-694`,
  posted at `:626-631`).

No reason is captured and no manager approval is required anywhere in Odoo.

**URY tells the kitchen by diffing two item arrays and emitting a second KOT.**
`sync_order` snapshots the pre-save items into `past_item` (`ury_order.py:1517-1525`),
replaces `invoice.items` wholesale, saves, and then calls `kot_execute(invoice, customer,
table, items, past_item, comments)` (`:1577`). Inside
(`ury/ury/api/ury_kot_generate.py:335-405`):

- `compare_two_array(current, previous)` returns per-item **deltas** — for an item present
  in both, `qty` becomes `current - previous`, which can be negative (`:409-423`).
- `get_removed_items` returns items whose `item_code` vanished entirely (`:427-433`).
- Positive deltas → a normal KOT, typed `"New Order"`, or `"Order Modified"` if a
  submitted KOT already exists for this invoice and production unit (`:162-171`).
- Negative deltas plus removed items → a **cancel KOT** with naming series
  `"CNCL-" + kot_naming_series` and type `"Partially cancelled"` (`:389-402`).
- Items are fanned out per **URY Production Unit** by item group, so the tandoor and the
  bar each get only their own lines, and a line whose item group belongs to no production
  unit produces a visible `msgprint` warning rather than silently vanishing
  (`:134-140`).
- One combined waiter slip is printed for all KOTs created in that pass (`:404-405`).
- The entire `kot_execute` call is wrapped in try/except that logs and continues — **a
  kitchen-printing failure must never fail the order save** (`ury_order.py:1576-1582`).

What URY *requires* to reduce a line: not a reason, but a **permission**. If the POS
Profile does not have `remove_items`, any decrease in a previously-sent item's aggregate
quantity throws `"You are not permitted to reduce or remove items from this order."`
(`ury_order.py:1537-1560`). Read the comment at `:1544-1548`: they compare **aggregates
per item_code, not per line**, because the same dish can appear on several lines with
different comments or courses, and a per-line comparison let a genuine reduction slip
through as long as no single line's qty fell. That is a scar.

Cancelling a whole order does require a reason: `cancel_order(invoice_id, reason)` stores
it on `cancel_reason` (`ury_order.py:1888`, `:1921`, `:1940`), releases the merge cluster
*before* touching the invoice (`:1909-1911`), fires a full cancel KOT for every item and
sets every submitted `URY KOT` for the invoice to `docstatus=2`
(`:2103-2153`), and only then cancels — through the standard Frappe workflow if submitted
(so GL reversals and audit entries happen) or by direct SQL if still draft, because Frappe
refuses to cancel drafts (`:1920-1940`).

**SambaPOS is the strictest.** Every order line has `Locked` (`samba/Order.cs:32`).
`LockTicket()` sets `Locked = true` on every unlocked order (`Ticket.cs:522-530`) — this
is what "sent to kitchen" means. Then:

- `CanCancelSelectedOrders` returns false if **any** selected order is locked, or has an
  Id > 0 (i.e. has ever been persisted), or is not in this ticket
  (`Ticket.cs:487-491`). You can only cancel lines you added in this un-submitted gesture.
- `GetUnlockedOrders()` is the only editable set (`Ticket.cs:493-496`).
- `MergeOrdersAndUpdateOrderNumbers` only merges orders that are `!Locked && Id == 0`
  (`Ticket.cs:498-515`) — a sent line is never silently folded into a new one.
- `CanRemoveSelectedOrders` additionally refuses to remove more value than remains unpaid
  (`Ticket.cs:482-485`) — you cannot void a line that has already been paid for.
- Every order state change carries `UserId` and `LastUpdateTime`
  (`samba/OrderStateValue.cs:20-25`), so who-changed-what-when is in the state itself.

## 6. Session and ticket lifetime

**Odoo's unit is the cashier session (`pos.session`), and it is a hard gate.**

- You cannot close the session while any draft order exists: *"You cannot close the POS
  while there are still draft orders for the day."* — raised in
  `action_pos_session_closing_control` (`pos_session.py:391-392`) and returned again as a
  soft refusal from `_cannot_close_session` (`pos_session.py:725-726`), which also hands
  the UI the actual `open_order_ids` so the cashier can go and clear them
  (`pos_session.py:613-617`).
- **Rescue sessions.** If an order arrives for a session that is already
  `closing_control`/`closed`, the server does not reject it. `_get_valid_session` logs a
  warning, finds any open session for the same config and reparents the order to it, and
  only raises if there is none (`pos_order.py:31-53`, called at `pos_order.py:71-73`).
  Separately `pos.session.rescue` (`pos_session.py:84`) marks a recovery session; if two
  cashiers race to close, the loser gets a message saying sales made in the meantime were
  saved into a Rescue Session (`pos_session.py:727-737`). A rescue session cannot be
  closed from the POS front end at all (`pos_session.py:399-401`).
- Tickets themselves do **not** expire. A table open for six hours is just a draft order.
  The only time-related concept is `preset_time` for scheduled orders, and that *extends*
  lifetime past close rather than cutting it short (§2).
- "The same sitting" is `_get_open_order`: for a restaurant config, an incoming draft with
  a `table_id` matches on `uuid` **or** `(table_id, draft, config_id)`
  (`pos_restaurant/models/pos_order.py:17-22`). So the table itself keeps a sitting
  together across devices, and two waiters opening the same table converge.
- Floors and tables cannot be deleted or archived while a session is open
  (`pos_restaurant.py:32-42`, `:131-138`) or while draft orders sit on them
  (`:79-87`, `:123-129`). Even archiving a *product* is refused while a draft order
  references it (`tests/test_pos_restaurant_flow.py:47-99`).
- Odoo also refuses to *change* a floor's config or active flag while a session is open
  (`pos_restaurant.py:44-56`), and `floor_ids` is in `_get_forbidden_change_fields`
  (`pos_restaurant/models/pos_config.py:17-20`).

**URY's unit is the POS Opening Entry**, per branch *and room*. `pos_opening_check()`
resolves the current room's open entry via a join on `Multiple Rooms`
(`ury_order.py:1674-1716`). Closing has an ordering rule: if multiple cashiers are
enabled, the **sub cashier must close first** — the main cashier's closing entry throws
`"Sub Cashier POS must be closed"` if a sub entry is still open
(`ury/ury/hooks/ury_pos_closing_entry.py:11-33`) — and a sub cashier is forbidden from
making a closing entry at all (`:61-71`). Closing amounts are summed across sub closings
(`:37-58`).

URY does not expire a table ticket either, but it **measures** it. `latest_invoice_time`
is stamped on the table when the invoice is created and cleared on release
(`ury_order.py:1586-1593`). From that: a service-line view computes minutes-since-seated
per table and a stage from the KOT status
(`ury/ury/api/ury_service_line.py:21-50`), and a dashboard raises a medium-severity alert
for tables occupied over 60 minutes and a high-severity one for orders pending payment
over 15 (`ury/ury/api/ury_dashboard.py:96-115`). The six-hour table is not killed; it is
escalated to a human.

Only URY's **self-ordering** (QR) sessions expire — a configurable
`session_idle_timeout_minutes`, default 30, sliding on each use
(`ury/ury/api/self_ordering.py:207`, `:219`, `:256-265`); on expiry the guest is told to
rescan.

**URY's optimistic-lock on the ticket** is worth its own line: `sync_order` takes a
`last_modified_time` from the client and compares it against `invoice.modified`, parsing
both with and without microseconds, and returns `{"status": "Failure"}` with *"This order
has been modified. Please reload the page"* on mismatch (`ury_order.py:1395-1425`). If the
client sends no `last_modified_time` at all and a live unprinted invoice exists, it
refuses with *"Table {0} is already occupied. Please refresh the page."*
(`:1426-1435`). Both are bypassed for a billing user.

## 7. Things we would not have thought of

Each of these is a guard clause that only exists because something happened in a real
restaurant.

- **Two waiters, one table, one order.** URY's `restrict_existing_order` before_insert
  hook refuses to create a second draft invoice on a table that already has one
  (`ury/ury/hooks/ury_pos_invoice.py:216-227`) — a DB-level backstop behind the optimistic
  lock. It has to carve out two exceptions: bill splits (`:199-200`) and the split child
  (`:202-214`).
- **The same dish on two lines hides a reduction.** URY compares aggregate quantity per
  `item_code`, not per line, with a comment saying the per-line version let real
  reductions through (`ury_order.py:1544-1553`).
- **A branch-assigned captain is not assigned to a room called None.** `getRoom()` returns
  `room=None` for a branch-level assignment; treating that as a room name wrongly locked
  out a real captain. The fix, and the comment recording the live E2E test that found it,
  is at `ury_order.py:1385-1393`.
- **The kitchen printer must never fail the order.** Both URY's KOT call
  (`ury_order.py:1576-1582`) and its KOT table re-stamp (`:1769-1774`) swallow every
  exception. Odoo's equivalent is `_send_order()`, a deliberate no-op hook
  (`pos_order.py:1597-1599`).
- **A stale tablet must not re-print the kitchen slip.** Odoo's serverDate comparison on
  `last_order_preparation_change` (`pos_order.py:396-416`).
- **The client may re-CREATE a line that already exists.** On sync, Odoo scans the
  incoming `lines`/`payment_ids` commands and rewrites any `CREATE` whose `uuid` already
  exists on the order into an `UPDATE` of that line (`pos_order.py:110-128`). Without it, a
  retried sync doubles the order.
- **Lines must be written before the state flips.** Odoo explicitly writes lines and
  payments *before* the rest of the order vals, with a comment: "Save lines and payments
  before to avoid exception if a line is deleted when vals change the state to 'paid'"
  (`pos_order.py:108-110`).
- **Never trust the client's paid amount.** `order.write({'amount_paid':
  order._compute_amount_paid()})` — "Recompute amount paid because we don't trust the
  client" (`pos_order.py:194-195`). Then: underpayment on a paid/done order raises;
  overpayment only logs a warning line (`pos_order.py:618-622`).
- **A refund may only draw from one order.** `sync_from_ui` raises "You can only refund
  products from the same order" if the incoming refund lines point at more than one
  refunded order (`pos_order.py:1290-1292`).
- **"Delete an order" means cancel-then-delete.** Odoo's `remove_from_ui` sets state to
  cancel first so the UI notification fires, then unlinks
  (`pos_order.py:1529-1542`); the ondelete guard does the same
  (`pos_order.py:551-561`). And cancelled orders are pushed to clients as *force-delete*
  instructions, because a client that still has them in memory will resurrect them
  (`pos_config.py`, `read_config_open_orders`: "Cancelled orders must be forced deleted
  from the user interface").
- **Deleting the last line frees the table — but not if a customer was attached.**
  Dolibarr deletes the whole draft invoice when its last line goes, *unless* a non-default
  thirdparty was already selected, with issue number #38219 in the comment
  (`dolibarr/invoice.php:1109-1126`). Odoo has the mirror-image test,
  `test_delete_line_release_table` (`test_frontend.py:914-921`).
- **Delete-with-no-line-selected deletes the last line.** Dolibarr handles the case where
  another device already removed the selected line, by falling back to
  `ORDER BY rowid DESC LIMIT 1` (`invoice.php:1093-1104`).
- **An entity assignment keeps an unpaid ticket alive.** SambaPOS `CanCloseTicket()`
  returns true when remaining is zero **or** the ticket has any entity attached **or** it
  is empty (`Ticket.cs:758-761`). A walk-in with no table cannot be parked.
- **Closing is not the same as being closed.** `Ticket.UnLock()` refuses to unlock a
  closed ticket (`Ticket.cs:77`), and `Close()` refuses while any product timer is still
  running (`Ticket.cs:79-86`).
- **Zero-amount transactions are only swept once closed** (`Ticket.cs:816-820`).
- **The short kitchen token wraps.** Odoo's `tracking_number` is `seq % 1000`
  (`pos_config._get_next_order_refs`). Over a long day you will see the same token twice;
  the real key is the uuid.
- **Two parallel syncs need to be distinguishable in the log.** Odoo mints a random
  `sync_token` per `sync_from_ui` call purely so the log lines interleave readably
  (`pos_order.py:1281-1282`), and gates full-payload logging behind an
  `ir.config_parameter` (`pos_order.py:1265-1266`).
- **A deleted partner should not sink the order.** If the incoming `partner_id` no longer
  exists, Odoo nulls it and turns off `to_invoice` rather than throwing
  (`pos_order.py:78-84`).
- **The merged-tables cache drifts.** URY re-derives it from the table graph on read,
  write and merge (`ury_order.py:306-330`, `:350-358`, `:786`, `:1499`).
- **Settling one of two merged bills must not free the table.** URY checks the whole group
  for open invoices before releasing (`ury_order.py:508-524`, called at `:2094-2098`), and
  hops from a secondary merged bill to its primary first (`:2085-2092`).
- **Splitting a payment across two merged invoices.** URY walks the payment list and gives
  each invoice `min(amount, its remaining)` in turn, with a re-entrancy flag
  `frappe.flags.in_bill_merge_sync` so the on_update hook that syncs merged invoices does
  not recurse (`ury_order.py:2032-2065`; hook at
  `ury/ury/hooks/ury_pos_invoice.py:229-292`, which also swallows and logs all errors so a
  sync failure cannot block a settlement).
- **A transferred party keeps its clock.** URY writes the *invoice's original* creation
  time as the new table's `latest_invoice_time` (`ury_order.py:1756-1757`), so the
  "occupied 60+ minutes" alert is not reset by a table move.

## What I would steal, ranked

1. **The merge cluster as a symmetric graph on the table, with the bill's copy treated as
   a derived cache and reconciled on every read/write** (URY `ury_order.py:26-141`,
   `:306-358`). It is the only donor design that survives a table being merged while an
   order is live, and it makes "which bill owns this table" a single BFS.
2. **A printed snapshot of what the kitchen has seen, plus a server-side staleness check
   before overwriting it** (Odoo `last_order_preparation_change` +
   `_ensure_to_keep_last_preparation_change`, `pos_order.py:305`, `:396-416`). This is the
   whole of "what does the kitchen get told" and the whole of the double-print defence, in
   one field.
3. **Diff-to-KOT: positive deltas become an add-KOT, negative deltas and vanished items
   become a cancel-KOT, fanned out per kitchen station by item group**
   (`ury/ury/api/ury_kot_generate.py:335-405`, `:112-190`). And compare aggregates per
   item, not per line (`ury_order.py:1544-1553`).
4. **`sent` as a per-line lock, with cancel/merge/edit all keyed off it** (SambaPOS
   `Order.Locked`, `Ticket.cs:487-515`). Dolibarr's version — a *separate permission* to
   touch a sent line (`invoice.php:1184`) — is the same idea expressed as authorisation,
   and both are worth having.
5. **The optimistic lock on the ticket: client sends the modified-timestamp it last saw,
   server refuses and tells it to reload** (`ury_order.py:1395-1435`). Cheap, and it is
   the only thing standing between two waiters and a lost round.
6. **A transaction-shaped move: permission → refuse-if-merged → refuse-if-cross-branch →
   refuse-if-destination-occupied → flip destination → flip source → move the bill →
   re-stamp only the *unstarted* KOTs** (`ury_order.py:1719-1774`, `:2156-2173`). Steal
   the order of operations and the "only re-stamp what has not been cooked" rule; do the
   whole thing in one Firestore transaction, which URY does not.
7. **"At least one item must remain on the original bill"** (`ury_order.py:590-591`) and
   **"cannot move more than the available quantity"** (`:581-584`). Two lines, two whole
   classes of broken split.
8. **Un-merge refused while any table in the cluster has a live bill** (`:473-478`), and
   release-on-payment gated on "no open invoice remains anywhere in the group"
   (`:508-524`).
9. **A dedicated, sticky `has_deleted_line` flag that the client cannot clear**
   (`pos_order.py:373`, `:607-608`) plus a per-line `is_edited` on qty *decrease*
   (`:1740-1746`). A cheap tamper-evident trail that costs two booleans.
10. **Takeaway as a pseudo-table** (URY `is_take_away`, `ury_order.py:771-775`). One flag
    buys the counter the whole table lifecycle for free, and keeps `order_type` derived
    rather than chosen.
11. **Escalate the six-hour table, do not expire it** (`ury_dashboard.py:104-115`,
    `ury_service_line.py:21-50`). A table open too long is a floor problem, not a data
    problem.
12. **The day-close refusal that hands back the offending order ids**
    (`pos_session.py:613-617`). "You have 3 open tables" is useless; "table 4, 9 and 12"
    is actionable.
13. **Scheduled orders survive day close by detaching from the session**
    (`pos_session.py:619-624`). If we ever do advance/pre-orders, this is the trick.

## What I would not steal

- **Odoo's `restaurant.table.parent_id` merge.** A single parent pointer plus a silent
  cycle-rollback (`pos_restaurant.py:140-150`) means merge failures are invisible to the
  cashier, and it cannot express "these three tables are one party" without a fragile
  chain. URY's symmetric graph is strictly better.
- **URY's `custom_merged_tables` CSV and its `LIKE %table%` lookups**
  (`ury_order.py:341-346`, `:441-451`, `:734-739`). `T-1` matches `T-10`. Use an array
  field and `array-contains`.
- **URY's non-transactional table flips.** `db.set_value` on both tables happens before
  `pos_invoice.save()` in `table_transfer` (`:1754-1767`), and the merge writes N table
  rows then commits (`:112-139`). This only survives because Frappe runs on one MariaDB
  with a request-scoped transaction and an on-premise box. We have per-document writes
  across a network; this must be one Firestore transaction or it will tear.
- **Odoo's rescue sessions** (`pos_session.py:84`, `:399-401`, `:727-737`). They exist
  because an on-premise POS can have a session closed underneath it by another terminal
  while offline orders are still in flight, and because every session must produce a
  balanced journal entry. Our day-close is not an accounting posting; a rescue session
  would be ceremony without a payoff.
- **Everything hanging off `account.move` / `account.journal`.** Odoo's order lifecycle
  drags in invoice creation, anglo-saxon costing, stock pickings, fiscal positions and
  reversal moves (`pos_order.py:821-1231`). URY's equivalent is that the running tab *is*
  an ERPNext POS Invoice, which is why it has `docstatus`, submit/cancel semantics and GL
  hooks for free. We have neither accounting spine; do not pretend to.
- **Dolibarr's "the table is encoded in the invoice ref string"**
  (`invoice.php:222`, `:795-798`). Charming, and the derived-occupancy idea is genuinely
  good, but the table id inside a text key is unindexable and unrenameable.
- **URY's mandatory-customer rule** (`ury_order.py:1437-1440`) — unless we want the GST
  behaviour it buys. If we do adopt it, adopt the house "Walk-in Customer" record too
  (`self_ordering.py:600-602`); a mandatory field with no default is just a blocked
  cashier at 21:00.
- **URY's "printing the bill is mandatory before settling"**
  (`ury/ury/hooks/ury_pos_invoice.py:106-114`). A thermal-printer assumption baked into a
  state machine.
- **SambaPOS's `TicketEntity` bag.** Modelling table, customer, driver and room as one
  untyped polymorphic list (`Ticket.cs:620-645`) is elegant and makes every query a scan.
  Steal the *idea* that the table is an attachment rather than a type; do not steal the
  bag.
- **Odoo's `nb_print`-based payment lock** (`pos_order.py:623-624`). Tying an edit rule to
  a hardware side effect is the wrong axis; tie it to a `billed` state instead.

## Where Odoo and URY disagree — the real decisions

| | Odoo | URY | The decision |
|---|---|---|---|
| **Customer on a ticket** | optional, `partner_id` nullable (`pos_order.py:325`) | mandatory, throws twice (`ury_order.py:1437`; `hooks/ury_pos_invoice.py:80-86`) | Do we want a party on every bill for GST? If yes, a house walk-in customer is required, not optional. |
| **Order kind** | not a field; a table or no table, plus a config bundle (`preset_id`) | a first-class enum branching in ~9 places | Enum only where behaviour genuinely differs. Aggregator yes; takeaway no. |
| **Takeaway** | an order with no table and a name (`floating_order_name`) | a table with `is_take_away=1` | URY's is cheaper and keeps one code path. Odoo's is cleaner conceptually. I would take URY's. |
| **Merge shape** | single `parent_id` chain on the table, cycle-guarded silently | symmetric CSV graph + BFS + invoice-side cache | URY. |
| **Merge preconditions** | none in the backend at all | different room / already-merged / occupied / two live orders — all refused | URY. Write these four refusals down as tests. |
| **Un-merge** | not modelled server-side | manual, all-or-nothing, refused while any bill is live; release-on-pay is separate and does not un-merge | URY. Note the deliberate split between *release* (free the tables) and *un-merge* (dissolve the group). |
| **Release one of three tables** | n/a | **cannot** (`ury_order.py:462-491`) | Is partial release a real floor need? Both donors say no. |
| **Move a merged table** | unconstrained | refused; unmerge first (`:1745-1746`) | URY. |
| **Reducing a sent line** | allowed, logged to chatter if `order_edit_tracking` is on | blocked by POS Profile `remove_items`, else allowed and KOT-cancelled | Odoo audits, URY authorises. We want both: audit always, authorise over a threshold. |
| **Reason for a void** | never captured | only on whole-order cancel, `cancel_reason` (`:1888`, `:1921`) | Neither donor requires a reason per line. If we do, we are ahead of both. |
| **Manager approval** | none anywhere | role-based, from POS Profile role tables, checked server-side with an explicit "the frontend gate is UX only" comment (`:1728-1742`) | URY, and copy the comment. |
| **Ticket lifetime** | draft forever; session close is the hard gate | draft forever; open-entry close is the gate; long tables escalate on a dashboard | URY's escalation. Both agree: do not expire a sitting. |
| **Same sitting** | the table is an identity in the order lookup (`pos_restaurant/models/pos_order.py:17-22`) | one draft invoice per table, enforced by a DB-existence hook (`hooks/ury_pos_invoice.py:216-227`) | Same answer by two routes. Enforce "one open ticket per table" at the write, not just at the read. |
| **Concurrency** | uuid unique constraint + CREATE→UPDATE rewrite + a serverDate comparison on the kitchen snapshot | client-supplied `modified` timestamp compared server-side | Take both. Odoo's is idempotency, URY's is a lock. They solve different halves. |
| **Day close with open tables** | hard refusal, returns the open order ids | no equivalent check found; closing is a cash-reconciliation ceremony with a sub-cashier ordering rule | Odoo's refusal. It is the one thing that keeps the data honest. |
