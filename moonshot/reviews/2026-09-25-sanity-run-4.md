## New findings

### S4-1 · P3 · The kitchen ticket's header overflows at phone width, clipping the age

*Scene.* 20:05. A cook checks the Live screen on a phone. Table 7's ticket header reads "tbl_meg_7". The age badge
next to it is cut off after the clock icon, so the cook can't see how long the ticket has waited. In the debug build,
a yellow-and-black "RIGHT OVERFLOWED BY 13 PIXELS" stripe covers the corner.

*Steps from a clean seed.* Re-import MockData7. Check out one dish on `tbl_meg_7` (guest app, or
`floorstate.mjs 7 ordered`). Start the kitchen app (`run_app.sh kitchen`). Open it at 430×900 (the `ab` viewport) and log in as
`kitchen@meg.test`. Look at card `kitchen-cart-<orderId>_0`.

*Expected.* The table and the age both fit on the card's header. The card should show the age, because the kitchen
works to that number.

*Seen.* Screen: pill "tbl_meg_7", then only the clock icon and a clipped "m", then the overflow stripe
(screenshot on the driver's machine, `scratchpad/kitchen-ready.png`). Console:
"A RenderFlex overflowed by 13 pixels on the right … Row: `active_cart_card.dart:40:15` … constraints w<=135.0".
Database: not involved.

*Reproduced (AGENT_QA §7).* Table 8, from `floorstate.mjs 8 ordered`. That helper orders Butter Naan, so the dish changed
too, but the header holds only the table and the age. I used a fresh browser at the same 430×900. Card "tbl_meg_8 now 1x
Butter Naan #0 PENDING". The console showed "A RenderFlex overflowed by 19 pixels on the right" at the same
`active_cart_card.dart:40:15`, with w<=135. At 1280×720 the same card fits: "tbl_meg_8" and "1m" both show. So the
bug is on narrow screens only. The seed still holds table 8's order `VFkLe5UtfuqQVnhDoshQ` (guest session
`17mFix3XZuRMkKEHByty`).

*Evidence.* Trajectory hops 2 and 8.

*Where to look.* `platter_kitchen/lib/widgets/active_cart_card.dart:40`: the header `Row` has no `Expanded` or
`Flexible`. The two-column grid (`live_orders_screen.dart:118`) leaves 135 px, and the raw id from TD-046 is long.
Showing "7" would probably hide the overflow, but it wouldn't fix it.

No other new findings. Everything else seen is already a TD row (above) or a note (below).

## Notes (not filed as bugs)

  landed on the dev home page ("QR: 10 … Test Menu Page") at `/?agent=1`. Setting `location.hash` by `$B js`, as
  `ab seed-consumer` does, reached the verify form. This is tooling, so it's a FRONTEND_TESTING §8 line, not a finding.
- The consumer's route dropped to `/?agent=1` after checkout, while the page showed the order. Same as run 2.
- **Table 2 has two words for one state.** The till floor says "2 signing in" and the waiter's Tables tab says

  waiter reads the status. Both are right from their own side. It's close to TD-042 / TD-044, and a floor exploration
  would decide it.
- **Table 5 isn't on the till floor.** The waiter lists it as "DISABLED", and the till leaves it out. That is by
  design as far as this run can tell.
- **`ab login server|kitchen` printed "no field login-restaurant"** on the second visit. Both staff apps had kept
  their login, so no form was drawn. The first server login printed "timed out / no login-submit" on a login that
  worked (AGENT_QA §8).
- The guest session's `endedAt` is stored as a `{_seconds,_nanoseconds}` map, and the line's `placedAt` as epoch-ms.
  This is the known emulator-sentinel gotcha.
- Kitchen Mark Ready is still recorded against `system` (run 3's note). Not re-checked.
- **Environment noise:** a client this run didn't start polled `order-getActiveCartsForKitchen` all run with dead
  session `tYvFcfQWOnqwANHbzr1G`. That is the same id as in run 3. It was told apart by the session id. This run's
  kitchen polls all succeeded, so step 7's "No Active Tickets" is a real read.
- The waiter's Served tab didn't list table 7's cart. That is emulator-only (AGENT_QA §8).

## What this run proved about the method

- The full spine runs through all four apps in one run on one 16 GB machine with no bypass. It takes one headless
  tab, one app server at a time, and about 12 minutes. That includes the app restarts, which were the slowest part.
  The next spine can be a script plus a short driver.
- Starting each app only when its step comes up worked. State lives in the backend, so the waiter and kitchen apps
  came back for step 7 with nothing lost.
