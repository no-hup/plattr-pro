# BL · Billing & tax — build plan (draft for Shaurya, 2026-09-15)

**Job.** Turn a table's placed lines into a legal bill: GST block, liquor VAT block, bill-level discount spread across lines, round-off, an unbroken invoice number, freeze on print, cancel, credit note, reprint. Payments are PY. Day close is DC. Printing bytes are KT.

## What exists today, honestly

- **No tax anywhere.** No menu item carries a tax label. No code computes GST or VAT. Money in the old code is float rupees rounded to two decimals; ST's new code is integer paise.
- **Line snapshot does not exist.** The order doc stores per-unit `priceInfo {basePrice, discount, finalPrice}` per item, plus a single order-level offer discount and percentage "charges". Nothing per line says which tax block, what rate, what the tax parts are, or where a discount came from.
- **ST writes to a stand-in** `restaurants/{id}/lines/{lineId}` with `listPrice, sent, v, discount, void, offer, countsTowardTotal` (TD-008).
- **Golden fixture** covers item and checkout pricing (24 rows), nothing about tax or bills.

So BL is the first module that forces the line snapshot into existence. The critical-pieces doc ranks that as the most expensive thing to get wrong, so it comes first and gets your signature before code.

## Calls I will make unless you say otherwise

- **Tax block is config, item carries only a block id.** `config/settings.tax.blocks.{food,liquor}` each with `mode` (inclusive or exclusive), `parts` (CGST 2.5 + SGST 2.5; VAT at the rate the CA gives), and a default SAC. Item gets `taxBlockId`, variants and add-ons inherit unless set. Rates are never literals.
- **A line without a tax block cannot be billed.** Preview shows the line in red, finalise refuses. No default block, as the critical-pieces doc says.
- **Money is integer paise** everywhere in new code, as in ST. Old order fields untouched.
- **Bill discount is spread by taxable value before tax**, share stored on each line so a credit note reproduces it exactly.
- **Round-off is one signed row on the payable**, `billing.roundToPaise` default 100, 0 turns it off.
- **Printed and unpaid → cancel** (PIN, reason, number kept). **Paid → credit note** (new doc referencing the bill; the refund is PY's).
- **Split by lines is BL.** Move lines between two bills in one transaction, re-run tax on both, no re-pricing. Splitting one amount three ways is a payment split and lives in PY.
- **Reserved offline ranges are designed for, not built.** The counter doc has the shape; OF fills it.
- **Out of scope v1:** e-invoicing and IRN (B2B over the turnover threshold only), dynamic B2C QR (₹500 Cr turnover), tips, customer GSTIN validation (captured as an optional string, nothing more), liquor excise register export.

## Answers so far (Shaurya, 2026-09-15 evening)

1. **Tax labels: set manually in Admin.** So AD gets a "tax block" picker on the item, and BL refuses to bill a line without one. No import work.
2. **Snapshot at checkout: my call.** Taking the in-transaction hook. Consumer impact: none visible. The order doc the Flutter apps read is unchanged; checkout additionally writes one `lines/` doc per item. The only risk is checkout getting slower by one batched write, and failing if that write fails, which is the behaviour we want (no bill without lines).
3. **Service charge removable per bill.** Not handled today: `billing.charges` is stamped on the order at checkout and nothing removes it. In BL it becomes a bill-level row the cashier can drop before finalise (a P1 audit row, no PIN), and a finalised bill is cancelled and re-issued, never edited. Goes into the sheet as a scenario.

## Open questions (answer in chat; each changes the work)

1. **Menu tax labels.** No dish has one. For the first customer, do labels arrive with the Petpooja import per category, or does the owner set them in Admin? Both need the `taxBlockId` field on menu items now, which is an MN schema change taken early.
2. **Snapshot at checkout.** Phase 5 adds one hook inside the existing checkout transaction. The alternative, a Firestore trigger, touches no old code but is async, so a bill could be requested before its lines exist. I recommend the hook. Your call, it is an existing dir and a schema addition.
3. **Service charge.** The old `billing.charges` percentage exists. Keep it as a bill-level row, default off, taxed in the food block? The tax treatment is the accountant's answer, not mine.
