# Donor review — taking money through an external device or service (UQ / UPI dynamic QR)

Date: 2026-09-17. Donors read: `ury/`, `odoo/addons/point_of_sale/`, `dolibarr/`, `samba/`,
`erpnext/`. Written blind to our own spec.

Paths below are relative to `/Users/shaurya/Desktop/moonshot/donors/`.

---

## 0. The headline: nobody open-sourced this

**No donor has a working integration with an external payment device or service.** Not one.

- **URY** — Indian product, Bangalore — ships the *interface* and says so in a header comment
  that is worth reading in full: `ury/ury/ury/api/payment_terminal.py:4-35`. "This is
  intentionally an interface only, not a working integration… Building a fake implementation
  against unverifiable assumptions would be worse than no implementation — it would look done
  without being done." The only concrete provider is
  `_SimulatedPaymentTerminalProvider` (`:92-146`) which marks everything `Approved` instantly,
  and it is explicitly never the default (`:149`, `:153-158`).
- **Odoo** core carries the *abstraction* (`use_payment_terminal`, `payment_method_type`) but
  `_get_payment_terminal_selection()` returns `[]` — `odoo/addons/point_of_sale/models/pos_payment_method.py:11-12`.
  Every real adapter (Razorpay, Adyen, Stripe, Six, Mercury) is a separate addon, and **none of
  them are in this clone** (`ls odoo/addons/` → `point_of_sale`, `pos_discount`, `pos_hr`,
  `pos_restaurant` only). The Razorpay integration exists only as a boolean that installs a
  module we do not have: `odoo/addons/point_of_sale/models/res_config_settings.py:36`.
- **Dolibarr** TakePOS records payment locally against a bank account, full stop
  (`dolibarr/invoice.php:415-460`). No device, no callback.
- **SambaPOS** is pure in-memory ticket arithmetic — `AddPayment` appends and recomputes
  `RemainingAmount` (`samba/Ticket.cs:251-259`). No external anything.
- **ERPNext** clone is root-level files only; `payment_request` is not present, so URY's
  reliance on it (below) cannot be read here.

### Does anything know about UPI?

Grepped the whole tree for `upi|razorpay|paytm|phonepe|vpa`. Results, honestly:

| Hit | What it actually is |
|---|---|
| `ury/ury/ury/api/payment_terminal.py:8` | a comment listing Pine Labs / Razorpay POS / PayTM / Ezetap as vendors *not* integrated |
| `ury/ury/ury/api/payment_terminal.py:81` | error string: "use a card/UPI reader at the counter" |
| `ury/frontend/src/data/forms/configure.json:30` | setup copy: "Set up payment methods like Cash, Card, UPI." |
| `odoo/.../res_config_settings.py:36` | boolean to install an absent module |

**That is the entire Indian-payments content of five mature POS codebases.** There is no VPA
handling, no dynamic-QR string builder, no webhook verifier, no `merchantTransactionId`
anywhere. For UPI dynamic QR specifically we are on our own — this is the finding, not a gap
in the search.

The closest structural analogue that *does* exist is Odoo's **`qr_code` payment method type**
(section 3), and it is deliberately trust-based, which is itself instructive.

## 1. The in-doubt payment

### URY — the state exists, the resolver does not

There **is** a distinct pending state. `URY Payment Terminal Transaction` has
`status: Pending | Approved | Declined | Cancelled`, defaulting to `Pending`
(`ury/ury/ury/doctype/ury_payment_terminal_transaction/ury_payment_terminal_transaction.json`,
`status` field). The interface contract requires the same four
(`ury/ury/ury/api/payment_terminal.py:52-53`, where `Error` replaces `Cancelled`) and mandates
non-blocking start + poll:

> "Implementations should be non-blocking where the vendor SDK allows it (poll via
> `get_transaction_status` rather than blocking the request thread for however long a customer
> takes to tap/swipe/insert a card)." — `payment_terminal.py:54-56`

**Who resolves a stuck `Pending`? Nobody.** There is no sweeper, no timeout, no scheduled job,
no expiry field on the doctype (`created_at` exists, nothing reads it). The transaction
controller is an empty `pass` — `ury_payment_terminal_transaction.py:8-12`. The doctype grants
`URY Cashier` **read/select only, no create or write** (permissions block in the JSON), so a
cashier cannot even hand-resolve one. A `Pending` row sits there forever until a System Manager
or URY Manager edits it in the Frappe desk UI.

Worse for our purposes: **the transaction log is never joined to the invoice's payment.** The
settlement path (`make_invoice`, `ury/ury/ury/doctype/ury_order/ury_order.py:1997-2077`) appends
`{mode_of_payment, amount}` rows and submits. It never looks at `URY Payment Terminal
Transaction`. The two systems are parallel and unreconciled.

The one honest thing here is the default provider: it **throws** rather than returning a
falsy success — `_NoOpPaymentTerminalProvider.start_transaction` at `payment_terminal.py:79-83`,
with the docstring "makes the interface's existence visible in behavior (a clear, honest error)
rather than silently pretending a terminal is available" (`:75-77`), and a test that locks that
in: `ury/ury/ury/api/test_payment_terminal.py:22-25`
(`test_default_provider_is_honest_not_silent`).

### URY — the online/link path punts to ERPNext

`create_payment_request()` (`ury/ury/ury/api/self_ordering.py:776-848`) creates an ERPNext
`Payment Request` and returns `{payment_request, amount, currency, payment_url, status}`.
`get_payment_status()` (`:855-871`) is a **pure read of `Payment Request.status`** — it does not
call the gateway, does not re-verify, does not time out. Settlement is explicitly someone
else's job, per the module header at `:762-772`:

> "Settlement-on-payment (webhook -> Payment Entry -> invoice submit) is ERPNext core's own
> responsibility once a real Payment Gateway Account is configured… **this module does not
> reimplement or verify gateway webhooks itself.**"

So even the pay-by-link flow has no in-doubt handling in URY. The QR/link and the
gateway-redirect are deliberately one code path — `:759-763`: "A gateway-redirect checkout and
a shareable/QR 'payment link' are the SAME Payment Request underneath; they only differ in how
the frontend presents `payment_url`." That collapsing is a good idea and I would steal it.

### Odoo — no pending state at all, by design

`pos.payment` has a `payment_status` field (`odoo/addons/point_of_sale/models/pos_payment.py:40`)
— a bare `Char`, no selection, no constraint. Core writes it never; the absent terminal addons
write it. The only core code that reads it is a guard (section 4).

Odoo's actual position is that **a `pos.payment` row existing means the money was taken.**
`action_pos_order_paid` (`pos_order.py:874-902`) compares `amount_paid` to `amount_total` and
either flips state to `paid` or raises "Order %s is not fully paid" (`:888`, `:898`). There is no
third outcome. An in-doubt terminal response is resolved *in the browser*, by the cashier, before
a `pos.payment` row is ever created — and that JS is not in this sparse clone.

### The one in-doubt mechanism Odoo does have: the rescue session

This is the best idea in the whole review and it is not about payments at all — it is about a
*late answer*.

`pos.session.rescue` — "Auto-generated session for orphan orders, ignored in constraints"
(`pos_session.py:84-87`). When an order arrives for a session that is already closed,
`_get_valid_session` (`pos_order.py:32-52`) logs a warning naming the session, the uuid and the
total, then **reparents the order onto whatever session is currently open**, and raises only if
there is none (`:50-52`). And when two users race to close, the loser is told exactly what
happened rather than being blocked:

> "The session has been already closed by another User. All sales completed in the meantime have
> been saved in a Rescue Session, which can be reviewed anytime and posted to Accounting from
> Point of Sale's dashboard." — `pos_session.py:731-737`

**This is the shape of the answer for a UPI callback that lands after day close.** Do not drop
it, do not refuse it, do not reopen the closed day: park it somewhere named, visible, and
postable later.

## 2. Duplicate protection

### Odoo: a client-generated UUID, unique at the database level

The key is a `uuid4()` **minted in the browser** (defaulted server-side if absent) and carried
through every sync. Both the order and each payment have one:

- `pos.order.uuid` — `pos_order.py:369`, constraint `pos_order.py:388`
  (`unique (uuid)`, "An order with this uuid already exists")
- `pos.payment.uuid` — `pos_payment.py:44`, constraint `pos_payment.py:46`

`sync_from_ui` (`pos_order.py:1269-1320`) resolves it and branches three ways
(`:1296-1309`):

1. existing + `draft` → update it
2. no existing → create
3. existing + **not** draft → **ignore the sync entirely**, return the existing id. The comment
   is a scar: `"# In theory, this situation is unintended / # In practice it can happen when
   'Tip later' option is used"` (`:1305-1306`).

Lookup is `search([('uuid','=',...)], limit=1, order='id desc')` — `pos_order.py:1258-1259`.

The subtlest bit is line-level: a re-sent `Command.CREATE` for a line whose uuid already exists
on the order is **rewritten into a `Command.UPDATE`** rather than creating a twin
(`pos_order.py:118-123`). That is idempotency at the child-row level, which is exactly what a
retried "record this payment" call needs.

Every sync run gets a random `sync_token` stamped into the logs purely to tell two concurrent
calls apart (`pos_order.py:1281-1282`). Cheap; I would copy it.

And the server never trusts the client's arithmetic:
`# Recompute amount paid because we don't trust the client` — `pos_order.py:194`.

### Dolibarr: no key, a balance clamp instead

TakePOS has no idempotency key. It protects by **remaining balance**: if the invoice is already
validated and nothing is left to pay, it refuses with "InvoiceIsAlreadyValidated"
(`dolibarr/invoice.php:374-381`), and when it does record a payment it clamps the amount:

```php
if ($amountofpayment <= 0 || $amountofpayment > $remaintopay) {
    $payment->amounts[$invoice->id] = $remaintopay;   // invoice.php:431-432
}
```

It then re-reads the balance from the database after writing (`:458`) rather than reasoning
about it in memory. Crude, and it silently swallows an overpayment rather than reporting it —
but it means a double-submit cannot book twice the money.

A second guard sits above all of it: if a cash control has already been closed for the day, the
payment action is refused outright (`dolibarr/invoice.php:304-309`).

### URY: accidental idempotency, and a real hole

`make_invoice` does `invoice.set("payments", [])` before appending
(`ury/ury/ury/doctype/ury_order/ury_order.py:2030`, and `:2039` for the merged-bill target), so a
retry **replaces** the payment lines instead of doubling them. Good — but it is a side effect of
wanting to recompute, not a stated intent, and it does not survive the submit: the second call's
`invoice.submit()` fails and is re-thrown as a bare string,
`frappe.throw(f"Error while settling order: {e}")` (`:2074-2077`). The cashier sees a stack
fragment and has no way to tell "already settled" from "settle failed".

**There is no protection at all against a guest genuinely paying twice** in any donor. Dolibarr's
clamp is the closest thing, and it resolves the situation by quietly discarding the second
payment.

## 3. Callback vs polling

**Polling, everywhere. No donor implements a callback.**

- URY's interface is poll-shaped by contract: `get_transaction_status(transaction_id)` "Called by
  the kiosk while it waits for the customer to complete the physical tap/swipe/insert"
  (`payment_terminal.py:60-64`). **No interval, no timeout, no retry budget is specified
  anywhere** — the interface leaves it entirely to the caller, and no caller exists.
- URY's link flow: `get_payment_status(session)` (`self_ordering.py:855-871`) is a polled read of
  a doctype field. Webhooks are named and explicitly disclaimed (`:762-767`).
- Odoo core: nothing. The terminal addons carry the polling loops.

**What happens to a late response: undefined in every donor**, except by accident via Odoo's
rescue session (section 1) and via `sync_from_ui`'s "ignore a sync for a non-draft order"
branch (`pos_order.py:1303-1309`), which is the closest thing to "the answer arrived after we
gave up — keep what we have."

`cancel_transaction` carries the only honest comment about racing:

> "Best-effort cancel of a pending terminal transaction (e.g. the customer walked away).
> Implementations should treat this as **advisory — a terminal may have already captured payment
> by the time cancellation is requested.**" — `payment_terminal.py:66-71`

That is the whole in-doubt problem in three lines, acknowledged and then not solved.

### Odoo's QR method — the closest thing to our UPI QR, and it is pure trust

`payment_method_type = 'qr_code'` ("Bank App (QR Code)") —
`pos_payment_method.py:14-18`, `:61`. `get_qr_code(amount, …)` builds a **base64 QR carrying the
exact amount** off the journal's bank account, via `res.partner.bank.build_qr_code_base64` with
`qr_code_method` selecting the scheme (EPC, SEPA, and in a full Odoo install, UPI):
`pos_payment_method.py:242-253`. Config is validated hard at save time — bank journal required,
bank account required, method required, and the scheme's own validator must pass:
`pos_payment_method.py:202-212`.

And then: **nothing confirms it.** There is no status field, no polling, no callback, no
transaction id. The guest scans, shows the cashier their phone, the cashier taps to record a
`pos.payment`. Mature, widely deployed, and it resolves the in-doubt payment by making a human
look at a screen.

One detail there is genuinely clever:

```python
# Generate QR without amount that can then be used when the POS is offline
pm.default_qr = pm.get_qr_code(False, '', '', pm.company_id.currency_id.id, False)
```
— `pos_payment_method.py:236-240`, wrapped in `try/except UserError` so a misconfigured method
degrades to `False` instead of breaking the POS load. The amount-less QR is precomputed and
shipped to the client in the POS payload (`_load_pos_data_fields` includes `default_qr` —
`:82`), so a till with no network can still show *a* QR and let the guest type the amount.

## 4. The manual override

**No donor has a "it paid, trust me" flow with a reason, a reference number or a manager gate.**
Searched for PIN / approval / override across all five.

What exists instead:

- **Odoo's whole QR flow is the override** — see above. The cashier's judgement *is* the
  confirmation, unlogged, un-gated, no reference captured.
- **Odoo's session-close override** is real and is the pattern worth copying (section 5).
- **URY denies the override**: `URY Cashier` has read-only permission on `URY Payment Terminal
  Transaction` (JSON permissions block), so a cashier cannot mark a stuck payment Approved.
  Nothing else can either.
- **URY's cancel is the only reason-carrying action**: `cancel_order(invoice_id, reason)` —
  `ury_order.py:1885-1940`. It gates on `frappe.has_permission(…, "cancel", doc=…)` (`:1891-1895`)
  **and** on branch match (`:1898-1905`), then writes `cancel_reason` (`:1918`, `:1926`, `:1940`)
  and cancels through the document workflow "so `on_cancel` hooks run and GL/payment reversals
  and audit entries are produced" (`:1921-1923`).
  ⚠️ **Live bug**: `pos_invoice.cancel()` is called at `:1919` *and again* at `:1924` inside the
  `docstatus == 1` branch, which can only be reached if the first call did not change docstatus.
  Do not copy this shape.
- **URY's discount override** is the one place a role check guards a money decision at settle
  time: `make_invoice` re-checks roles server-side against
  `DISCOUNT_ALLOWED_ROLES` (`ury_order.py:1942-1950`, enforced at `:2019-2022`) with the comment
  "Server-side authorization for the discount applied in make_invoice" — i.e. the frontend gate
  was found insufficient. Note `URY Cashier` is *in* the allowed set, so it is a role check, not
  an escalation.

Odoo's one relevant hard guard is a **print lock**:

```python
raise UserError(_('You cannot change the payment of a printed order.'))
```
— `pos_order.py:623-624`, fired when `nb_print > 0` and any incoming payment command has a
`payment_status` that is not `'cancelled'`. Once the guest has the receipt in hand, the tender
is frozen. This is the only core Odoo code that reads `payment_status` at all, and its shape
("a cancelled payment may still be edited, a live one may not") reads like it was added after
someone silently re-tendered a printed bill.

Two neighbouring guards from the same `write()`:
- paying **less** than the total while in `paid`/`done` → hard `UserError`
  (`pos_order.py:618-620`)
- paying **more** → not an error, a logged chatter line: "Warning, the paid amount is higher
  than the total amount. (Difference: %s)" (`:621-622`)

Asymmetric on purpose. Underpayment is a bug; overpayment is a fact you record and move on from.
Every payment change is posted to the order's chatter via `_create_pm_change_log`
(`pos_order.py:632-640`) — a permanent audit trail on the document itself.

## 5. Reconciliation

This is where the donors are actually mature, and it is all at **day close**.

### Odoo: per-payment-method declared difference, posted to P&L

`close_session_from_ui(bank_payment_method_diff_pairs)` — `pos_session.py:597-641`. The signature
tells the story: `list[(payment_method_id, diff_amount)]`. The cashier declares, **per non-cash
payment method**, the gap between what the system thinks was taken and what the provider/bank
actually shows.

Each declared gap becomes its own two-line journal entry:
`_create_diff_account_move_for_split_payment_method` (`pos_session.py:680-696`), referenced
`"Closing difference in %(payment_method)s (%(session)s)"` (`:697`), debiting the method's
outstanding account and crediting its journal's **profit or loss** account depending on sign
(`_get_diff_vals`, `:699-716`).

The close is **refused** if the relevant profit/loss account is not configured, and the error
names the journals: `_cannot_close_session`, `pos_session.py:738-756`. Cash has its own parallel
path — `cash_register_difference` (`pos_session.py:69-72`, computed `:263`) posted as a statement
line labelled "Cash difference observed during the counting (Loss/Profit) - closing"
(`_post_statement_difference`, `:486-524`).

So: **a mismatch is never silently absorbed, and it is never a blocker either.** It is declared,
named, and booked to a real account. The manager sees it in the P&L.

Sitting above that, a threshold: `amount_authorized_diff` with `set_maximum_difference`
(`pos_config.py:121`, `:166-169`) — "the maximum difference allowed… **for non-POS managers**.
If this maximum is reached, the user will have an error message at the closing of his session
saying that he needs to contact his manager." Shipped to the client at
`pos_session.py:817`. Small gap → cashier closes. Big gap → a manager has to be involved.
**That is the manager-override gate we were looking for in section 4 — Odoo puts it on the
day's total, not on the individual payment.** I find that more convincing than per-payment
approval: it is one decision per day instead of one per incident, and it still catches the
cashier who pockets a UPI payment.

Odoo also refuses to close over unfinished work — draft orders block
(`pos_session.py:724-725`, and again in `action_pos_session_closing_control` at `:310-312`),
invoices must be posted (`_check_invoices_are_posted`, called `pos_session.py:435`).

And when the accounting itself does not balance, there is an explicit escape hatch: the
**"Force Close Session"** wizard (`pos_session.py:583-595`), reached after an
`env.cr.rollback()` so the half-built close is not committed (`:583-586` — the comment explains
that picking records were already created and must not survive the failure). Its message is
honest: "There is a difference between the amounts to post and the amounts of the orders, it is
probably caused by taxes or accounting configurations changes." The force path routes the
imbalance to a chosen balancing account, and the account field is read-only unless you are in
`account.group_account_readonly` (`:588-590`).

### URY: the same shape, plus visible incident scars

`ClosingPaymentTable` shows, per mode: **Opening / Expected / Closing / Difference**
(`ury/pos/src/components/ClosingPaymentTable.tsx:34-90`). `Expected` is aggregated client-side
from the session's invoice payment rows (`POSClosingDialog.tsx:101-130`), `Closing` is what the
cashier counts, `difference = closing - expected` with the sign convention pinned by comment
(`POSClosingDialog.tsx:350-357`, "Positive = overage, negative = shortage. Must match the display
convention in ClosingPaymentTable (Fix 1)"). Backend mirrors it at
`ury/ury/ury/hooks/ury_pos_closing_entry.py:37-55`.

A mismatch in URY **blocks nothing and posts nothing** — it is stored on the closing doc and
that is all. No profit/loss account, no threshold, no manager. URY's gate is different in kind:
draft invoices block the close (`sub_pos_closing.py:19-25`, "Submit/Delete Draft Invoices"),
sub-cashiers must close before the main cashier
(`ury_pos_closing_entry.py:11-31`), and the main cashier cannot file a *sub* close
(`sub_pos_closing.py:59-66`).

## 6. Refunds and reversals

**Local only. Nothing is ever pushed to a provider. No donor holds a refund credential.**

- **Odoo**: `_refund()` copies the order into a new one with `is_refund=True`
  (`pos_order.py:1425-1450`, values at `:1389-1402`). The money leaves via a normal negative
  `pos.payment` tendered at the till. Refund and original are linked both ways
  (`refunded_order_id` / `refund_orders_count`, `pos_order.py:364-366`, computed `:429-433`), and
  the invoice flips `out_invoice` ↔ `out_refund` by sign (`:926-928`). Where the money goes is
  decided by a three-case ladder with the cases spelled out in comments —
  `_get_partner_bank_id`, `pos_order.py:808-819`: refund/negative → the **customer's** bank,
  positive → the payment journal's bank, fallback → the company's — each filtered by
  `allow_out_payment` (`:812-813`). A returned cash payment requires a cash method to exist or
  the whole thing raises: "No cash statement found for this session. Unable to record returned
  cash." (`pos_order.py:199-201`).
- **URY**: no refund at all. `cancel_order` (`ury_order.py:1885-1940`) cancels the invoice through
  the Frappe workflow so reversals are generated downstream (`:1921-1923`), and records a
  `cancel_reason`. That is the entire reversal story.
- **Dolibarr**: negative-total invoices become credit notes, and it refuses to make one without
  finding a prior real invoice for that customer — "NoPreviousBillForCustomer"
  (`dolibarr/invoice.php:342-366`). A guard against a credit note conjured from nothing.

**Implication for us:** if we want an automatic UPI refund we get no help from any donor — not a
credential model, not a partial-refund flow, not an idempotency key for the refund call. What we
*can* copy is the linkage discipline: a refund is a first-class document that points at what it
reverses, in both directions.

## 7. Things we would not have thought of

Each of these reads like it followed an incident.

1. **"Tip later" makes a settled order re-sync.** `pos_order.py:1303-1309` — the branch that
   silently ignores a sync for a non-draft order exists because a real feature re-sends a paid
   order. Any "the POS re-sent me a payment for a bill that is already closed" path must be a
   no-op that returns the existing record, **not** an error and not a second write.

2. **Once the receipt is printed, the tender is frozen.** `pos_order.py:623-624`. And the guard
   deliberately lets a `payment_status == 'cancelled'` row through. Someone re-tendered a printed
   bill.

3. **Underpay = error, overpay = logged note.** `pos_order.py:618-622`. Do not treat the two
   symmetrically.

4. **Rounding tolerance is a payment concept, not a display one.** `action_pos_order_paid`
   accepts "not fully paid" when cash rounding is on and the gap is within half a rounding unit
   (HALF-UP) or one unit otherwise — `pos_order.py:891-899`. And `_get_rounded_amount`
   (`pos_order.py:786-806`) rounds **only the cash residual**: "Only round the residual settled in
   cash: non-cash payments pay their exact share" (`:800-804`). A UPI payment must carry the exact
   paise; the cash in the same split absorbs the rounding.

5. **A payment method cannot be edited while a session is open.** `_is_write_forbidden`
   (`pos_payment_method.py:139-141`) allows only `sequence`; anything else raises and **names the
   open sessions** (`:150-153`). Nobody swaps the VPA mid-service.

6. **Switching integration type wipes the other type's config.** `_force_payment_method_type_values`
   (`pos_payment_method.py:176-190`) nulls `qr_code_method` when you pick terminal and
   `use_payment_terminal` when you pick QR, on both create and write (`:143-174`). Prevents a
   method that is half-QR half-terminal.

7. **Cash methods cannot be shared across shops.** `_check_cash_method_single_shop`
   (`pos_payment_method.py:220-228`) — "Validation Error: You cannot assign the same Cash payment
   method to multiple POS Shops." The multi-outlet version of that for a shared VPA is worth
   thinking about now, not later.

8. **URY clears Frappe's queued message before throwing its own.** `self_ordering.py:820-831` —
   ERPNext's `make_payment_request` queues a raw msgprint ("Payment Entry is already created")
   into `frappe.local.message_log` *before* throwing, so it reaches the client alongside the
   clean message unless you `frappe.clear_messages()`. The comment also documents the real
   ERPNext quirk behind it (`:792-810`): for `POS Invoice`, `get_amount()` does not fall back to
   `outstanding_amount` and throws "already created" on a fresh unpaid draft. **A guest must
   never see the gateway's raw error.** We will hit exactly this with a PSP.

9. **"Payment Request created but no payment URL available" is a real, distinct state.**
   `self_ordering.py:834-843`: the request is valid, only the link failed — logged, surfaced
   plainly, "instead of fabricating a fake link." For us: the bill amount is locked in but the QR
   string failed to generate. That is not a payment failure and must not be reported as one.

10. **A blank input is not "reviewed and zero".** `POSClosingDialog.tsx:186-187` (Fix 2) and the
    blocking validation at `:304-335`: every row must be *explicitly touched*, and an all-zero
    close is refused outright. A cashier tabbing through a close was booking zeroes.

11. **Retry the submit, not the create.** `POSClosingDialog.tsx:189-192` (Fix 3) and `:360-401`:
    the draft doc name is persisted the instant it is created — "if the submit call below throws,
    a retry must skip straight to submitting this doc rather than creating a second draft"
    (`:399-403`). On explicit cancel the server-side draft is **deliberately left alone** and only
    the client stops tracking it (`:295-298`). This is the two-phase pattern a payment needs:
    the intent record survives the failure of the confirmation.

12. **Do not trust a cached profile for an authorization decision.**
    `POSClosingDialog.tsx:222-232` (Fix 4) — the main-cashier check re-fetches from the server
    because the `sessionStorage` copy could be stale if the assignment changed mid-session.

13. **Do not trap the cashier behind post-success housekeeping.**
    `POSClosingDialog.tsx:447-450` and `:468-472` (Fix 5) — the close is already submitted by the
    time the checklist gate renders, so a Skip was added to an otherwise non-dismissible
    full-screen overlay. Anything shown *after* the money is settled must be skippable.

14. **Clamp negatives in code, not in the input attribute.** `ClosingPaymentTable.tsx:21-26` —
    "the HTML `min="0"` attribute alone does not stop programmatic or pasted negative input."

15. **Odoo logs the orphan order's uuid and total before reparenting it.**
    `pos_order.py:32-38`. When money turns up in the wrong session you want the amount in the log
    line, not just an id.

## What I would not steal

- **URY's terminal abstraction as-is.** `payment_terminal.py` is a module-level global
  (`_payment_terminal_provider`, `:149`) with a whitelisted endpoint that swaps in the
  auto-approving simulator (`register_simulated_terminal_provider`, `:152-158`). A
  `@frappe.whitelist()` that installs an always-approves payment provider is a production
  footgun no matter how many comments say "testing only". If we build a provider seam, the
  simulator is selected by config or environment, never by an HTTP call.
- **A `Pending` state with no resolver.** URY's four-state enum with no sweeper, no expiry and a
  cashier who lacks write permission is worse than no state: it accumulates rows nobody can
  action. Either ship the resolver with the state or do not ship the state.
- **A transaction log that is not joined to the bill.** `URY Payment Terminal Transaction` is never
  read by `make_invoice` (`ury_order.py:1997-2077`). The payment record and the bill's tender line
  must be the same fact or reconciliation is theatre.
- **Dolibarr's silent overpayment clamp.** `invoice.php:431-432` discards the excess without
  telling anyone. Clamp *and* report.
- **Odoo's bare `payment_status = fields.Char`.** `pos_payment.py:40` — no selection, no
  constraint, written only by addons that may not be installed. Our status field gets an enum and
  a constraint.
- **URY's double `pos_invoice.cancel()`.** `ury_order.py:1919` + `:1924`.
- **Client-side aggregation of "expected".** URY computes the per-mode expected total in the
  browser from invoice payment rows (`POSClosingDialog.tsx:101-130`) and posts it to the server as
  fact. The number you reconcile against must be computed server-side, the way Odoo does
  (`pos_session.py:246-266`).
- **`frappe.throw(f"Error while settling order: {e}")`.** `ury_order.py:2076-2077`. A raw exception
  string in front of a cashier at the moment money is involved.

## Where the donors disagree

**Who confirms an unverifiable payment?**
Odoo says the cashier's eyes, at the moment of tender, with no record beyond the `pos.payment`
row (`pos_payment_method.py`'s whole `qr_code` path). URY says nobody may — the cashier has
read-only permission on the transaction log, so a stuck payment can only be resolved by a
manager in the back office.

**I find Odoo more convincing, but only because of what it pairs the trust with.** Odoo can
afford a trusting till because the money is reconciled per payment method at close, the gap is
booked to a real account, and a gap over the threshold pulls in a manager
(`pos_config.py:166-169`). Trust at the point of sale plus accounting at the end of the day.
URY has the per-mode difference table (`ClosingPaymentTable.tsx:34-90`) but it posts nowhere and
blocks nothing — so its strictness at the till buys nothing, and a cashier with a stuck ₹840 UPI
payment and a queue behind them will simply tender it as cash and pocket the note. **Strictness
at the moment of payment without reconciliation at close is the worst of both.**

**Idempotency key: client or server?**
Odoo: client-minted uuid, trusted for identity but never for amounts
(`pos_order.py:369` vs `:194`). URY: server-side, implicit, via "clear and re-append the payments
list". Odoo is right. The retry originates on the client, so the key has to as well — a
server-minted key is a different key on every retry, which is no key at all.

**Reconciliation as bookkeeping or as a gate?**
Odoo books the difference and lets you close (`_create_diff_account_move_for_split_payment_method`,
`:680-696`); URY records it and also lets you close, but with nothing behind it. Neither blocks.
Both are right to not block — a till that cannot close is worse than a discrepancy that is
written down — but only Odoo makes the discrepancy *cost* something by landing it in the P&L,
which is what makes anyone care about it the next morning.
