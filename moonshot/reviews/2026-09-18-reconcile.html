2. Drift check: did we stay simple?

Each row is the manager session's read. The main session adds its view in section 4.

The new code itself: fine.

Small layered modules, pure logic tested without the emulator, one door for PIN, one for config, one for errors. Restaurant differences are config keys, not code branches. This is what lets a Supabase or AWS move later be weeks, not a quarter. No sign of over-building here.

Two worlds, one seam. This is the real risk.

The old app code (cart, orders, table, session, about 3,000 lines of plain JS) still owns the spine: what a table is, when it frees, what an order's status means. The new modules bolt onto it through hooks. Every "two paths free a table by opposite rules" bug this week came from that seam (TD-013, TD-036, TD-037, TD-033).

Plain example: a captain taps "order complete" on the kitchen app at 20:44. The old code frees the table and ends the session. The new floor screen says a table with ₹2,340 unbilled is never free. Both are "right" in their own world. The guest walks out unbilled.

Why it matters for the future: takeaway, delivery, aggregator orders, counter service, a second till: every one of those lands on the session and order lifecycle. If that stays split across two worlds, each new requirement becomes a patch in both. That is the "major rewrite later" you are worried about, arriving slowly.

Two records of the same money.

Each order still stores its own totals in rupees as decimals (priceInfo), while the new billing sums exact per-line snapshots in paise. Four places decide "is this billable" differently. Today deleting the old copy is a schema change and a re-seed. After the first real order it is a year of history that disagrees with itself.

Order of building: back office first, front of house missing.

We built approvals, payments ledger, day close and offline before order entry, printing and setup. Not wrong: the money maths is the hard part and it is done well. But it means the demo you can give today is "close a day you could not trade". The order must flip now: tax on the menu, order entry, print, reports.

Process weight.

Per module: a spec sheet, a fan-out to three outside models, a blind Opus test list, a donor review of open-source POS code, then build. 21 documents, about 570 KB, for a product that cannot issue one bill. The thinking was good and it caught real bugs before code. But the sheets are now heavier than the code they describe, and a fresh agent spends its first 100k tokens reading. Some of this should be cut, not all.

Scope creep: mostly held.

UPI dynamic QR (a 63 KB sheet) is deferred, the first restaurant's soundbox covers it. Offline was cut to four items. Covers, sections, reopen-a-day, a second till: all said no or later, in writing. Good.

3. Decisions for you

Plain question, an example, the options, and what we recommend. Status updates as the thread runs. You can answer here in chat or in the manager session.

D1Who owns "when does a table free up"?

Example: table 7 has ₹2,340 unbilled. The captain taps Complete on the kitchen app. Should the table go free?

A. One owner: the new floor module. Recommended. The old "complete order frees table" path is removed or made to ask the floor module first. A table frees only when no money is open. Cost: a few hours, one characterization test on the old path. Gain: every future flow (takeaway, delivery, counter) has one rulebook.
B. Leave both, patch as bugs come. Zero work now. Each new flow is fixed twice, and the next bug is found by a guest walking out unbilled.
Recommend A. This is the most coupled thing in the system and the cheapest moment to fix it.

Status: decided 20 Sep: A. Floor module owns "table frees". Do it before order entry.

D2Delete the old money copy on orders?

Example: a ₹333 dish. The old copy stores 333.0 with tax as a decimal. The new line stores 33300 paise with CGST 833 and SGST 833. Reports built on the old copy will never match the GST bill.

A. Delete it now, re-seed. Recommended. Lines are the only truth. Old reads move to the lines. One-time cost, a day. Free only while we are not live.
B. Keep both. Nothing now. Permanent double bookkeeping once real orders exist.
Recommend A, and before order entry is built, because order entry sits right on top of this code.

Status: revised 20 Sep after a code check: the old total is read by 8 endpoints and shown by every app, so deleting it now is a week of old-code work. New rule instead: till, billing and reports never read it, only the line snapshots. Delete it when order entry ships and the old cart path dies.

D3How heavy should the process be from here?

Example: the floor screen took a 37 KB sheet, three outside reviews and a donor review before code. It found nine real defects before code, which was worth it. Order entry is next and is smaller than it looked.

A. Keep the sheet, keep ONE outside pass (the donor review), drop the three-model fan-out and the blind Opus list for modules smaller than billing. Recommended. Halves the reading and the documents. Keeps the part that caught the real bugs.
B. Keep everything. Safest, slowest, and the documents keep growing faster than the code.
C. Drop the sheets, code straight from a short plan. Fastest. Loses the "without this, what breaks" discipline that has been catching money bugs.
Recommend A. Also delete the three dated working files and four spent handoffs (already listed on the pickup list).

Status: decided 20 Sep: A. Keep the sheet plus one donor review. Delete the 3 dated working files and 4 spent handoffs.

D4Small leftovers, one word each
  • Covers. Ask "how many people?" when staff open a table? Yes costs one number pad. No means per-head average is lost forever for those nights. Our lean: yes, optional field.
  • Settled table timer. After paying, a table now frees only when the cashier taps Clear. You had chosen "also frees itself after 30 minutes". Keep Clear-only (simpler), or bring the timer back? Our lean: Clear-only.
  • stuff.md. Accounts and infra pointers. Into git, or local only?

Status: decided 20 Sep: covers yes (ask "how many people?" on open). Settled-table timer: Clear-only. stuff.md: local only, never in git.
