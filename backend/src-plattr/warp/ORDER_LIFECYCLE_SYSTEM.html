Order Lifecycle System Documentation

Complete order tracking flow from checkout to completion with status management

📦 Order Management 🍳 Kitchen Integration 👨‍🍳 Server Tracking 🔄 Real-time Updates 💳 Payment Status
📋 SPECS: Order Lifecycle System
Core Flow
SPEC-001Orders are stored at restaurants/{rid}/orders/{orderId}
SPEC-002Order is created via checkoutCart which validates session, stock, and prices
SPEC-003If active order exists for table (PENDING/IN_PROGRESS), new cart is appended to existing order
SPEC-004If no active order exists, new order is created with unique orderNumber (ORD-00001 format)
SPEC-005Cart is cleared after successful checkout (order creation)
SPEC-006Order number is auto-incremented using restaurants/{rid}/counters/orders document
SPEC-007All order operations use Firestore transactions for data consistency
SPEC-008SessionId is mandatory for checkout and linked to the order
Order Status Lifecycle
SPEC-010Order statuses: PENDING → IN_PROGRESS → COMPLETED | CANCELLED
SPEC-011New orders are created with status IN_PROGRESS (not PENDING)
SPEC-012COMPLETED status requires bill revalidation (recalculate prices from all carts)
SPEC-013When order is COMPLETED, paymentStatus is set to PAID
SPEC-014CANCELLED orders remain in database for audit trail
SPEC-015Status normalization maps legacy values: PLACED→PENDING, ACTIVE/PREPARING→IN_PROGRESS, COMPLETE→COMPLETED
Cart Status Lifecycle (within Order)
SPEC-020Cart statuses: PENDING → ACCEPTED → PREPARING → READY → SERVED
SPEC-021Special statuses: CANCELLED (from any state except SERVED), RETURNED (only from SERVED)
SPEC-022Cart status transitions are validated via VALID_TRANSITIONS map
SPEC-023Each cart maintains statusHistory array with timestamp and userId for each change
SPEC-024When cart is ACCEPTED, assignedTo field is set to the accepting user
SPEC-025CANCELLED and RETURNED are terminal states with no valid transitions
Data Structures
SPEC-030Order contains: restaurantId, tableId, orderNumber, orderStatus, paymentStatus, carts[], items[], priceInfo
SPEC-031Order.carts[] stores full cart snapshots with cartId, status, statusHistory, items, priceInfo
SPEC-032Order.items[] is a flattened list of all items across carts for direct access
SPEC-033Each cart has unique cartId format: {restaurantId}_{tableId}_{uuid8}
SPEC-034priceInfo uses OrderPriceInfo model: basePrice, finalPrice, totalDiscount, totalDiscountAmount
SPEC-035estimatedPrepTime calculated as: 10 + (itemCount × 2) minutes
Payment Status
SPEC-040Payment statuses: unpaid → partially_paid → paid
SPEC-041New orders start with paymentStatus: UNPAID
SPEC-042When orderStatus is set to COMPLETED, paymentStatus is automatically set to PAID
SPEC-043Bill revalidation compares recalculated prices with stored prices before completing
Validation Rules
SPEC-050Checkout validates: non-empty cart, valid session, items in stock, price consistency
SPEC-051getOrder requires either orderId OR tableId (with restaurantId)
SPEC-052updateCartStatus validates: orderId exists, cartIndex valid, status transition allowed
SPEC-053updateOrderStatus validates: orderId, orderStatus enum, sessionId (required)
SPEC-054Cart price recalculation triggered on item cancellation
Error Cases
SPEC-060NOT_FOUND (404): Order/Cart not found at specified index
SPEC-061FAILED_PRECONDITION (412): Empty cart, invalid session, items out of stock
SPEC-062INVALID_ARGUMENT (400): Missing required fields, invalid status value
SPEC-063FAILED_PRECONDITION (412): Invalid status transition attempted
SPEC-064FAILED_PRECONDITION (412): Bill mismatch during order completion
Cross-Entity Effects
SPEC-070Checkout clears cart document after order creation
SPEC-071Order completion triggers FCM notification to assigned server (if flag enabled)
SPEC-072Order links to session via sessionId for tracking
SPEC-073Order reads table.assignedServerId for server notification routing
SPEC-074Counter document incremented atomically for order number generation
Edge Cases
SPEC-080If cart clearing fails after order creation, order is still considered successful
SPEC-081Cart price recalculation on checkout if validation fails
SPEC-082Notes from multiple carts are concatenated with newlines
SPEC-083Existing order without orderNumber gets one generated on cart append
SPEC-084All carts SERVED triggers log but doesn't auto-complete order (manual completion required)

💡 Nuances & Edge Cases
✅ Validation Nuances
  • Session validation happens BEFORE checkout processing
  • Stock is validated at checkout time (double-validation from addItem)
  • Cart price recalculation if validation fails (auto-fix)
  • Price mismatch at completion blocks order completion
  • Status values are normalized (PLACED→PENDING, etc.)
🔄 State Management Nuances
  • All status changes maintain statusHistory with timestamps
  • Cart status transitions follow strict VALID_TRANSITIONS map
  • CANCELLED and RETURNED are terminal states
  • ACCEPTED status sets assignedTo field for tracking
  • All carts served doesn't auto-complete (requires manual action)
🔒 Transaction Safety
  • Order creation uses Firestore transaction
  • Order number generation is atomic (counter increment)
  • Cart status updates use transaction for consistency
  • Cart clearing after order is separate operation (may fail)
  • If cart clearing fails, order is still considered successful
⚡ Performance & Recovery
  • Estimated prep time: 10 + (itemCount × 2) minutes
  • Orders queryable by tableId or orderId
  • getActiveOrders excludes COMPLETED orders
  • Orders sorted by updatedAt (most recent first)
  • Server-assigned orders appear first in server view
💰 Price Handling
  • Order priceInfo aggregates all cart prices
  • Discount averaging across carts for order totalDiscount
  • Cancellation triggers price recalculation
  • OrderPriceInfo: basePrice, finalPrice, totalDiscount, totalDiscountAmount
  • Bill mismatch at completion = failed-precondition error
🔔 Notification Handling
  • Notifications gated by sendServerNotifications flag
  • FCM token fetched from server document
  • No notification if server has no fcmToken
  • Notification includes: title, body, data payload
  • FCM failures logged but don't fail the operation

❌ Error Handling
Scenario Code HTTP Message Recovery
Order not found not-found 404 Order not found Verify orderId exists
Cart index invalid internal 500 Cart at index {n} not found Use valid cart index from order.carts
Empty cart checkout failed-precondition 412 Cannot checkout an empty cart Add items to cart first
Invalid/inactive session failed-precondition 412 Invalid or inactive session Re-authenticate with valid session
Items out of stock failed-precondition 412 Items out of stock: {names} Remove out-of-stock items from cart
Invalid status transition internal 500 Invalid status transition from X to Y Follow valid transition path
Bill mismatch on complete failed-precondition 412 Recomputed bill does not match stored bill Investigate price discrepancy
Missing required fields invalid-argument 400 {field} is required Provide all required parameters
Invalid status value invalid-argument 400 status must be one of: ... Use valid status enum value
Non-active order update failed-precondition 412 Cannot update items in non-active order Order must be IN_PROGRESS
