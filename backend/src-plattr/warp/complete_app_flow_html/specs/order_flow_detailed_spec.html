📋 System Overview
Key Concepts
  • An Order represents the table's active bill/check
  • An order contains multiple Carts (checkout snapshots)
  • Each cart contains Cart Items (individual menu selections)
  • Orders are stored at restaurants/{rid}/orders/{orderId}
  • System supports continuous ordering – customers can checkout multiple times during a session, all carts aggregate into a single order
Only ONE active order per table at a time. New checkouts append to existing active order, not create new ones.
🆕 Order Creation Flow
📞 1. Entry Point: checkoutCart API
  • Triggered when customer clicks "Checkout" in app
  • Required params: restaurantId, tableId, sessionId
  • Optional: notes (special instructions)
✅ 2. Pre-Checkout Validation
  • Session Validation: Ensures sessionId is active and valid
  • Cart Validation: Cart must exist and have at least 1 item
  • Stock Validation: All items must be in stock at checkout time
  • Price Validation: Recalculates prices to ensure consistency
Stock is validated AGAIN at checkout (even if validated when adding to cart). This prevents race conditions where items go out of stock between add-to-cart and checkout.
📸 3. Cart Snapshot Creation
  • Generates unique cartId: {restaurantId}_{tableId}_{uuid8}
  • Sets cart status to PENDING
  • Records checkoutTime timestamp
  • Initializes statusHistory array with first entry
  • Calculates estimatedPrepTime: 10 + (itemCount × 2) minutes
  • Sets assignedTo: null (no kitchen staff assigned yet)
📝 4. Item Normalization
  • Extracts items from cart into simplified format for order
  • Skips cancelled items (status === 'cancelled')
  • Skips items without menuItemId
  • Uses BasicPriceInfo model for price standardization
  • Preserves: menuItemId, name, quantity, priceInfo, selectedVariants, selectedAddons
🔍 5. Active Order Check (Transaction)
  • Queries orders collection for this table
  • Looks for orders with status IN_PROGRESS or PENDING
  • Uses Firestore transaction for data consistency
This check determines whether to CREATE a new order or APPEND to existing. Critical for multi-cart support.
🆕 Scenario A: No Active Order
  • Generates new orderNumber using counter
  • Format: ORD-00001 (5-digit padded)
  • Counter stored at: restaurants/{rid}/counters/orders
  • Creates new order document
  • Sets orderStatus: IN_PROGRESS
  • Sets paymentStatus: UNPAID
  • Sets isActive: true
  • Stores cart in carts[] array
  • Stores normalized items in items[] array
New orders start with IN_PROGRESS status, NOT PENDING. The PENDING status exists in constants but is rarely used for orders.
📝 Scenario B: Active Order Exists
  • Appends new cart to existing order.carts[]
  • Merges new items into order.items[]
  • Recalculates total priceInfo across ALL carts
  • Concatenates notes with newline separator
  • Updates updatedAt timestamp
  • If existing order has no orderNumber, generates one now
  • Keeps same orderStatus: IN_PROGRESS
🧹 6. Post-Checkout: Clear Cart
  • Calls internal clearCartInternal() function
  • Deletes/clears the cart document at carts/{tableId}
  • Returns order details to client
Cart clearing is a SEPARATE operation from order creation. If cart clearing fails, the order is still considered successful. This prevents data loss.
🛒 Multi-Cart Orders
How Multi-Cart Works
  • Customers can checkout multiple times during a single session
  • Each checkout creates a new cart snapshot within the same order
  • All carts share the same orderNumber
  • Each cart has independent status tracking
  • Kitchen can process carts in parallel or sequentially
Multi-cart enables "order more" scenarios. Customers can order appetizers, then later order mains, all on the same bill.
💰 Price Aggregation Logic
Function: calculateTotalPriceInfo(carts)
  • basePrice: Sum of all cart base prices
  • finalPrice: Sum of all cart final prices
  • totalDiscountAmount: Sum of all cart discount amounts
  • totalDiscount: AVERAGE of all cart discount percentages
Discount percentage is AVERAGED across carts, not summed. This is intentional to prevent inflated discount display.

🔄 Order Status Lifecycle
Order Status Values
PENDING → IN_PROGRESS → COMPLETED
PENDING → CANCELLED
IN_PROGRESS → CANCELLED
Status Transitions
  • PENDING → IN_PROGRESS: Rarely used (orders start at IN_PROGRESS)
  • IN_PROGRESS → COMPLETED: Order is paid and closed
  • IN_PROGRESS → CANCELLED: Order is cancelled
  • COMPLETED and CANCELLED are terminal states
New orders are created with IN_PROGRESS status directly. The PENDING status exists for legacy compatibility but is not typically used as the initial state.
📦 Completing an Order (updateOrderStatus)
  • Called by server/admin to mark order as COMPLETED
  • Requires valid sessionId
  • Bill Revalidation: Recalculates prices from all carts
  • If recalculated price ≠ stored price → 412 FAILED_PRECONDITION
  • On success: Sets paymentStatus: PAID
  • Triggers server notification if feature flag enabled
Bill revalidation prevents tampering. If cart prices were modified after checkout, completion will fail.
📊 Status Normalization

Legacy/variant status values are mapped to standard values:

Input Value Normalized To
PLACED PENDING
ACTIVE, PREPARING IN_PROGRESS
COMPLETE COMPLETED
pending (lowercase) PENDING
in_progress (lowercase) IN_PROGRESS

📝 Status History Tracking
  • Every status change appends to cart.statusHistory[]
  • Entry format: { status, timestamp, userId, notes }
  • Provides complete audit trail of cart progression
  • When status = ACCEPTED, also sets cart.assignedTo = userId
🔔 Auto-Complete Check
  • When a cart becomes SERVED, system checks if ALL carts are now served/cancelled/returned
  • If all carts are in terminal state, a log is written
  • Order is NOT auto-completed – requires manual updateOrderStatus(COMPLETED) call
Auto-completion is intentionally disabled. Restaurant staff must explicitly mark order complete to ensure payment is collected.
✅ Validation & Input Handling
Input Validation Classes
  • OrderInputValidation: Validates order-related API inputs
  • Uses Firebase HttpsError for standardized error responses
createOrUpdateOrder Validation
  • restaurantId: Required, non-empty string
  • tableId: Required, non-empty string
  • cart: Required, must have items array with ≥1 item
getOrder Validation
  • restaurantId: Required
  • Either orderId OR tableId required
  • sessionId: Optional, validated if provided
updateCartStatus Validation
  • restaurantId: Required
  • orderId: Required
  • cartIndex: Required, non-negative integer
  • newStatus: Required, must be valid CART_STATUS enum
  • sessionId: Optional
updateOrderStatus Validation
  • restaurantId: Required
  • orderId: Required
  • orderStatus: Required, must be valid ORDER_STATUS enum
  • sessionId: Required (not optional)
sessionId is REQUIRED for updateOrderStatus, unlike other APIs where it's optional. This ensures only authenticated sessions can close orders.

Active Order Filters

Orders are considered "active" if status matches any of:

PENDING IN_PROGRESS pending in_progress PLACED PREPARING READY active ACTIVE
Multiple status variants are checked for backwards compatibility with legacy data.
getActiveOrdersForRestaurant (Kitchen/Server View)
  • Returns all non-COMPLETED orders for a restaurant
  • Requires valid sessionId
  • Optional serverId for filtering
Sorting Logic
  • If serverId provided: Orders assigned to that server appear first
  • Secondary sort: By updatedAt (most recent first)
  • Cart filtering: Excludes carts with SERVED status from response
  • Item sorting: READY status items appear first within each cart
Response Sanitization
  • Firestore Timestamp objects converted to ISO strings
  • Order status normalized using mapOrderStatus()
  • Cart status normalized using mapCartStatus()
  • Item data simplified for frontend consumption
🔢 Order Number Generation
  • Counter document: restaurants/{rid}/counters/orders
  • Field: currentCount (integer)
  • Format: ORD-{count} with 5-digit zero-padding
  • Examples: ORD-00001, ORD-00042, ORD-01337
  • Counter incremented atomically within transaction
  • If counter document doesn't exist, starts at 1
Counter increment is part of the order creation transaction. This prevents duplicate order numbers even under concurrent requests.
🔔 Server Assignment & Notifications
🚩 Feature Flag: sendServerNotifications
State Behavior
ON FCM notification sent when order is marked COMPLETED
OFF No notifications sent
Notification Flow (when COMPLETED)
  1. Read tableId from order
  2. Fetch table document, get assignedServerId
  3. Fetch server document, get fcmToken
  4. Send FCM notification via sendFCMNotification()
Notification Payload
{
  "title": "Order Completed",
  "body": "Order {orderId} marked complete – please collect payment",
  "data": {
    "restaurantId": "...",
    "orderId": "...",
    "type": "ORDER_COMPLETED"
  }
}
Edge Cases
  • If table has no assignedServerId: No notification sent
  • If server has no fcmToken: No notification sent
  • FCM failures are logged but don't fail the operation
