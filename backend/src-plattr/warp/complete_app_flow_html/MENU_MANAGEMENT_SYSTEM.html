📋 SPECS: Menu Management System

Complete Specification

Core Flow (SPEC-001 to SPEC-010)
SPEC-001
Menu is organized in 4-level hierarchy: Categories → Menu Items → Variants → Addons
SPEC-002
fetchMenu() is the primary API for consumer apps, takes restaurantId and optional inStock filter
SPEC-003
When inStock=true, only items/addons with isInStock=true are returned (default behavior)
SPEC-004
Categories are fetched ordered by 'order' field and must have a name
SPEC-005
Menu items are grouped by categoryId in the response structure
SPEC-006
Each menu item includes enriched variants and addons (denormalized for performance)
SPEC-007
Variants are fetched as a map (key: variantId) for O(1) lookup during organization
SPEC-008
Addons are filtered by isInStock during fetch, not during organization
SPEC-009
Response includes metadata with totalCategories and totalMenuItems counts
SPEC-010
All 4 collections fetched in parallel using Promise.all for optimal performance
Data Structures (SPEC-011 to SPEC-020)
SPEC-011
Category: {id, name, description, image, order}
SPEC-012
MenuItem: {menuItemId, meta{name, description, image}, categoryId, priceInfo{basePrice, discount, finalPrice}, variants[], addons[], isInStock, isCustomizable, nutritionalInfo, allergenTags}
SPEC-013
Variant: {id, meta{name, description}, options[{id, name, priceInfo}], isMandatory, respectParentDiscount?}
SPEC-014
Addon: {id, meta{name, description}, priceInfo{basePrice, discount, finalPrice}, isInStock, isMandatory?, respectParentDiscount?}
SPEC-015
priceInfo always contains: basePrice (required), discount (optional, default 0), finalPrice (calculated)
SPEC-016
Menu items reference variants by {id, name} - name stored at item level for variant groups
SPEC-017
Menu items reference addons by addonId string only (denormalized during fetch)
SPEC-018
Organized menu structure: {categories: [], menuItems: {categoryId: [items]}, metadata: {}}
SPEC-019
Missing variant IDs are filtered out (graceful degradation if variant deleted)
SPEC-020
Missing addon IDs are filtered out (graceful degradation if addon deleted)
Feature Flags (SPEC-021 to SPEC-030)
SPEC-021
isMultipleVariantOrAddonForMenuItemsSupported: Controls cart item consolidation in addItemToCart (NOT in menu fetch)
SPEC-022
No direct feature flags affect menu fetching logic
SPEC-023
Frontend determines display logic based on item.isCustomizable flag
SPEC-024
fallbackToSameCustomConfigurationForAddItem: Auto-fills last configuration when re-adding item
SPEC-025
Menu CRUD operations (add/update/delete) not gated by feature flags
SPEC-026
Stock availability is data-driven (isInStock field), not flag-driven
SPEC-027
Reserved for future menu-related flags
SPEC-028
Reserved for future menu-related flags
SPEC-029
Reserved for future menu-related flags
SPEC-030
Reserved for future menu-related flags
Validation Rules (SPEC-031 to SPEC-040)
SPEC-031
restaurantId is required for all menu operations
SPEC-032
Restaurant must exist in Firestore (404 if not found)
SPEC-033
Category name is mandatory (throws error if missing during fetch)
SPEC-034
Menu item creation requires: meta.name, categoryId, priceInfo.basePrice
SPEC-035
Variant creation requires: meta.name, priceInfo.basePrice
SPEC-036
Update operations validate field types if present (e.g., basePrice must be number)
SPEC-037
menuItemId required for update/delete operations
SPEC-038
isAvailable field for stock update must be boolean
SPEC-039
Input validation handled by MenuValidation singleton class
SPEC-040

Error Cases (SPEC-041 to SPEC-050)
SPEC-041
404 NOT_FOUND: Restaurant doesn't exist
SPEC-042
404 NOT_FOUND: Menu item doesn't exist (update/delete operations)
SPEC-043
400 INVALID_ARGUMENT: Missing required fields (restaurantId, menuItemData, etc.)
SPEC-044
400 INVALID_ARGUMENT: Category name missing during fetch
SPEC-045
500 INTERNAL: Generic error for unexpected failures in menu fetch
SPEC-046
All errors logged with context (restaurantId, menuItemId, stage)
SPEC-047
CRUD operations use ErrorHandler singleton for consistent error responses
SPEC-048
Failed Promise.all in fetch returns first error encountered
SPEC-049
Organization errors (missing variants/addons) handled gracefully with filtering
SPEC-050
Frontend must handle empty menuItems arrays for categories with no items
Cross-Entity Effects (SPEC-051 to SPEC-060)
SPEC-051
Menu fetch is READ-ONLY, no side effects on any entities
SPEC-052
addMenuItem creates document in /restaurants/{rid}/menuItems/{auto-id}
SPEC-053
updateMenuItem modifies existing /restaurants/{rid}/menuItems/{mid}
SPEC-054
deleteMenuItem removes document from /restaurants/{rid}/menuItems/{mid}
SPEC-055
updateMenuItemAvailability only updates isInStock field (partial update)
SPEC-056
Deleting a variant doesn't cascade-delete references in menu items (gracefully filtered)
SPEC-057
Deleting an addon doesn't cascade-delete references in menu items (gracefully filtered)
SPEC-058
Cart operations reference menuItemId but don't mutate menu entities
SPEC-059
No FCM notifications triggered by menu CRUD operations
SPEC-060
Menu changes are not real-time propagated to active consumer sessions
Edge Cases (SPEC-061 to SPEC-070)
SPEC-061
Empty categories array returns valid response with empty menuItems object
SPEC-062
Categories with no items return empty array for that categoryId
SPEC-063
Menu item with no variants/addons returns empty arrays (valid state)
SPEC-064
Variant with no options still returned (frontend must handle)
SPEC-065
inStock filter applies to both menuItems AND addons independently
SPEC-066
Item marked out-of-stock after user views menu: handled at addToCart validation
SPEC-067
Price changes after menu fetch: recalculated at checkout, not at addToCart
SPEC-068
Concurrent CRUD operations: Firestore handles optimistic locking
SPEC-069
Large menus (100+ items): consider pagination in future (not currently implemented)
SPEC-070
Menu fetch time increases linearly with number of items (no caching implemented)

restaurants/{restaurantId}/variants/{variantId}
Read: id, meta (name, description), options[], isMandatory, respectParentDiscount
Write: CRUD operations (managed via variant APIs)
READ WRITE (CRUD)
➕ Addons
restaurants/{restaurantId}/addons/{addonId}
Read: id, meta, priceInfo, isInStock, isMandatory, respectParentDiscount
Write: CRUD operations (managed via addon APIs)
READ WRITE (CRUD)
Entity Relationships: Menu Items reference Categories (categoryId), Variants (variant.id array), and Addons (addon string array). Denormalization happens during fetchMenu for performance.
🚩 Feature Flags
🔀 isMultipleVariantOrAddonForMenuItemsSupported

ON: Cart consolidates items with identical configurations (increments quantity)

OFF: Each addItemToCart creates a separate cart entry

Impact: Affects cart behavior, not menu fetch

Default: ON
🔄 fallbackToSameCustomConfigurationForAddItem

ON: Auto-fills last selected configuration when re-adding same item

OFF: Always shows blank customization modal

Impact: UX convenience, doesn't affect menu data

Default: ON
📦 inStock Query Parameter

true: Returns only items/addons with isInStock=true

false: Returns all items regardless of stock status

Impact: Data-driven filter, not a feature flag

Default: true
Menu flow itself has NO direct feature flags. Flags listed affect downstream operations (cart, customization).

💡 Nuances & Edge Cases
Validation Nuances
  • → restaurantId validation happens before Firestore query (fail fast)
  • ⚠ Category name missing throws error DURING fetch, not during validation (side effect of map)
  • → inStock parameter defaults to false internally (explicit check: inStock !== false)
  • ✓ MenuValidation class provides centralized validation for consistency
  • ⚠ CRUD operations validate BEFORE existence check (different order than fetch)
Data Structure Nuances
  • → Menu items store variant references as {id, name} - name is variant GROUP name, not option name
  • → Addon references in menu items are string IDs only (simpler structure)
  • ✓ Response denormalizes for performance: clients don't need additional lookups
  • ⚠ Missing variant/addon IDs silently filtered (no error) - could hide data integrity issues
  • → finalPrice calculated as (basePrice - discount), NOT stored separately in DB
Stock Management Nuances
  • → inStock filter applies at QUERY level for performance (WHERE clause, not post-filter)
  • ⚠ Item can be in-stock but have all addons out-of-stock (still returned)
  • ⚠ Stock status NOT re-validated when adding to cart (race condition possible)
  • ✗ If item goes out-of-stock after menu fetch, caught at checkout, not addToCart
  • ✓ updateMenuItemAvailability is partial update (only isInStock field)
Performance Considerations
  • ✓ Promise.all fetches 4 collections in parallel (~60% faster than sequential)
  • → Variants stored as map for O(1) lookup during organization (100+ items benefit)
  • → Addons stored as map for O(1) lookup during organization
  • ⚠ No caching implemented - every fetchMenu hits Firestore (consider Redis for high traffic)
  • ⚠ Large menus (500+ items) may hit Firestore read limits - pagination not implemented
  • → Categories ordered by 'order' field at query level (efficient)
Edge Case Recovery
  • ✓ Empty categories array returns valid response (graceful degradation)
  • ✓ Category with no items returns empty array (not null)
  • ✓ Deleted variants/addons filtered out without breaking response
  • ✗ Category name missing throws hard error (breaks entire fetch)
  • ⚠ Frontend must handle empty menuItems[categoryId] for display logic
Pricing Nuances
  • → respectParentDiscount flag on variants/addons affects CART price calculation, not menu display
  • ⚠ Price changes after menu fetch NOT communicated to user until checkout
  • → Discounts displayed in menu but recalculated at checkout for accuracy
  • ✓ Menu fetch returns both basePrice AND finalPrice for transparent pricing

🔔 FCM Notifications & Triggers
No FCM notifications or Firestore triggers for menu operations. Menu changes do not trigger push notifications or real-time updates to consumers. Clients must manually refresh to see menu changes.

🚨 Error Handling
Error Scenario HTTP Code Error Message User Experience Recovery Path
restaurantId missing 400 "Restaurant ID is required" Toast: "Invalid request" Developer error - fix API call
Restaurant not found 404 "Restaurant not found" Error page: "Restaurant unavailable" Check QR code / restaurantId validity
Category name missing 500 "Category name is missing" Toast: "Menu data error" Admin must fix category data
Generic fetch failure 500 "Unable to fetch menu" Error page: "Cannot load menu" Retry button, check network
Menu item not found (update/delete) 404 "Menu item not found" Toast: "Item no longer exists" Refresh menu list
Missing required fields (CRUD) 400 "Restaurant ID and menu item data are required" Form validation error Fill all required fields
Invalid field types 400 "Base price must be a number if priceInfo is provided" Form validation error Correct field type
Empty menu (0 items) 200 - Empty state: "No items available" Normal - restaurant setup incomplete
